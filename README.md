# 摸鱼桌宠 (desk-pet)

上班摸鱼用的桌面小挂件：桌面悬浮宠物 + 打卡 + 摸鱼收入实时统计。
侧边栏功能参考 [momoyu pro](https://pro.momoyu.cc/)：主页 / 摸鱼研究院 / 打卡记录 / 设置。

## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 壳 | Electron 38 | 透明置顶窗口、托盘、无边框拖拽 |
| 渲染 | Vue 3 + Vite 6 | 单份构建产物按 `?route=pet|panel` 挂载两个应用 |
| 存储 | `node:sqlite` | Node 内置，零外部依赖；表结构自带同步字段 |
| 图形 | 内联 SVG | 桌宠是手绘 SVG，无图片资源，可无限缩放 |
| 打包 | @electron/packager | 免安装单文件 exe |

> Electron 必须 ≥ 37（Node 22+），低版本没有 `node:sqlite`。

## 桌宠动画（2D 可动关节）

桌宠是**纯 2D**：`<img>` 切透明立绘 PNG，没有 3D、没有骨骼。
想要「动起来」有两个层次，成本差一个数量级，见下。

### 现状：动作与服饰是两个正交维度

素材只有**整张立绘**（`resources/yuki/*.png` → `prepare-yuki.js` 抠白底去水印
→ `resources/pet/yuki-<slug>.png`）。当前靠**换图**表达姿势：

- **动作** 18 张（挥手 / 打哈欠 / 睡觉 / 蹦跳…）→ `PET_EXPRESSIONS`
- **服饰** 20+ 套（便服 / 睡衣 / 旗袍…）→ `OUTFITS`

两者正交，不能混成一类 —— 服饰图只有一张，当动作图用会让表情全失效
（这条在 `interactions.js` 里写死了理由，别改回去）。
自动换装按时间挑，挂机时在池子里轮换。

### 已排除的路线：3D

试过 Meshy 图生3D + 自动绑骨 + 动画（三个独立计费 API，26 信用）。
**结论是不做**，原因是素材与玩法都不匹配：

- 现有 44 个 slug 是**独立整图**，3D 化后姿势必须改骨骼动画状态机，
  换装要从「换 PNG」升级成「材质/UV 切换」或准备 20 套模型 —— 数周工作量
- 桌宠常驻悬浮，3D 要持续占 GPU；实测 1.7 万面 34fps 尚可，
  但 Meshy 默认产出的 120 万面模型直接拖死核显
- 对话窗侧边立绘与手机端本来就该是 2D，3D 只惠及桌宠一个窗口

相关代码（`Pet3DViewer.vue` / `Pet3DLabView.vue` / `meshy-pet.js` /
`dev-3d.js` / `make-test-glb.js` / `three` / `undici` 依赖）已全部移除。

### 无头验证桌宠窗

桌宠是透明置顶无边框窗，肉眼不易核对渲染是否正确。主进程留了一个开关：

```bash
DESK_DEBUG_PORT=9222 npm run dev      # 然后 curl 127.0.0.1:9222/json/list
```

拿到 CDP 端点后可以量取窗口位置、派发鼠标事件、截图。
默认关闭，只有显式设了环境变量才生效。

## 手机版（PWA）

桌面版之外还有一个**手机版**，在 `mobile/`。两端**各自独立运行**：
手机不依赖电脑开机，数据存在手机本地。

```bash
node mobile/build.js     # 产出 dist-mobile/，上传到你的域名即可
node mobile/serve.js     # 或本地预览：手机连同一 WiFi 打开 http://<电脑IP>:8899
```

**共享逻辑、独立数据**：

```
mobile/chat.js ──▶ ../src/shared/{moyu,content,interactions}.js   ← 零复制
```

改桌面端的人设或时段表，手机端重新 build 就同步生效。
但对话记录和亲密度各存各的 —— 这是「互不依赖」的代价。

**为什么手机端不需要后端**：实测 DeepSeek 接口会回 CORS 头
（`access-control-allow-origin` 回显 Origin，`allow-headers` 含 authorization），
所以浏览器可以直连，不需要中转服务器。有些 API 不返回这些头，那种就必须中转。

**手机端没有的**：桌宠悬浮窗、挂机冒泡、打卡、摸鱼统计 ——
都依赖桌面环境（透明置顶窗口、常驻进程），移动 OS 不支持。

细节见 `mobile/README.md`。

## 打包产物

`npm run pack` 产出：

```
release/
  使用说明.txt
  摸鱼桌宠-win32-x64/
    摸鱼桌宠.exe        免安装，双击即用（唯一入口）
    resources/app.asar  应用代码与立绘
    *.dll / locales/    Electron 运行库
```

**只保留 exe 一个入口。** 早期版本还生成 `创建桌面快捷方式.vbs` 和 `启动.bat`，
三个都能启动反而让人不知道该点哪个；现在 build.js 会主动删掉这两个历史遗留文件。

注意 exe **不能单独拷出来**：Electron 在 exe 同目录找 `resources/`，
脱离文件夹会直接退出（实测过）。所以「一个 exe」指的是唯一入口，
而不是单文件。桌面快捷方式用系统自带的「发送到 → 桌面快捷方式」即可。

### 打包踩到的三个 Windows 坑（已在 build.js 里处理）

1. **`TEMP` 指向网络盘** → packager 的 rename 直接 EPERM。脚本把 `TEMP`/`TMP`
   强制指向本地 `%LOCALAPPDATA%\Temp\deskbuild`，并先在本地打包、再整体复制到 `release/`。
2. **Windows Defender 锁住刚解压的 `electron.exe`** → packager 收尾要 `rename` 解压目录，
   正好撞上扫描锁，稳定失败。脚本挂 `afterExtract` 钩子，反复「试 rename 再改回」
   直到锁释放（实测约 9s）再交给 packager 收尾。
3. **旧版程序还在运行** → exe / asar 被占用，清理 `release/` 时 `rmSync` 抛 EPERM。
   用户看到的是一段原始堆栈，完全看不出「程序没退出」这个真正原因。
   现在 `removeOutDir` 会把 EPERM/EBUSY 翻译成人话，并列出占用进程的 PID 与名字：

   ```
   ✗ 无法清理旧产物：Z:\Files\Apps\desk\release\摸鱼桌宠-win32-x64
     目录被占用，最常见的原因是「摸鱼桌宠」还在运行。

     检测到正在运行的相关进程：
       · PID 7872  摸鱼桌宠
       ...

     请先退出程序（右键桌宠 → 退出摸鱼桌宠，或托盘图标右键 → 退出），再重新运行 npm run pack。
   ```

   查进程走 PowerShell `Get-Process`，两个已踩过的坑写在 `listAppProcesses` 的注释里：
   必须显式设 `[Console]::OutputEncoding = UTF8`（否则中文进程名按 GBK 输出，
   Node 解出来是 `��������`）；语句间要用换行而非 `;`（`;` 会让 `|` 只作用于后半句，
   `ConvertTo-Json` 落空、退回表格输出，解析失败表现为「检测不到任何进程」）。
   查不到进程不影响打包 —— 整段逻辑失败即返回空数组。

另外 `tmpdir: false` 用于避开「`mkdtemp` 之后 rename 到已存在目录」这一在 Windows 上
必失败的动作。

## AI 对话

后端是 **OpenAI 兼容的 `/chat/completions`**（`src/main/chat.js`），用 Node 内置 fetch，
不引第三方 SDK。支持：

- **流式 SSE**：自己写的解析器（`parseSSE`），按 `\n` 切行累积 buffer，
  能正确处理「JSON 被 chunk 边界切断」和「多个 data 事件粘在一个 chunk」两种情况——这两种
  在真实网络下都会发生，是流式解析最常见的 bug 来源，`scripts/chat-test.js` 专门覆盖。
- **取消**：`AbortController` 按 `requestId` 存在 service 的 Map 里。
  注意 abort 可能发生在 `fetch()` 阶段**或**后续读取流的阶段，后者抛的是原生 `AbortError`，
  必须在读取循环外面 catch 并归一成 `ChatError(kind:'aborted')`，否则前端拿不到统一类型。
- **错误翻译**：401/402/404/429 等状态码翻译成中文，并尽量提取上游 `error.message`。
- **上下文**：只取最近 N 条**且排除 `error=1` 的消息**，避免把报错文本当成对话历史喂回去。

配置存在 `settings` 表（`chatBaseUrl` / `chatApiKey` / `chatModel` / `chatPersona` 等），
`chatApiKey` 只落本地库，不下发到渲染进程（`chatStatus()` 只返回 `hasApiKey` 布尔值）。

本地地址（`127.0.0.1` / `localhost`）不强制要求 Key，方便接 Ollama。

### 长上下文

两个上限**叠加生效**，缺一不可：

| 设置 | 默认 | 作用 |
|---|---|---|
| `chatMaxHistory` | 100 条 | 按**条数**取最近 N 条（上限 400） |
| `chatMaxChars` | 48000 字符 | 按**字符预算**从最早开始丢（约 3 万汉字） |

为什么需要两个：条数控制不了长度（10 条长消息可能比 200 条短消息还大），
字符数控制不了结构（有的模型按条数算配额）。所以先按条数取，再按字符裁。

**关键细节**：`trimByChars` 的 `reserveChars` 参数会把 system 提示词的长度也扣掉。
不扣的话，人设越长实际请求越容易超预算——实测女友人设 820 字 + 历史 3000 字 = 3800，
设了 3000 却发出 3800。这个 bug 是 e2e 量出来的，单测覆盖不住。

裁剪永远**至少保留最后一条**（用户当前输入）：即使单条就吃满预算，
也不能裁空，否则模型没有输入可答。这是刻意行为，不是 bug。

### 角色设定

`CHAT_PERSONAS` 在 `src/shared/moyu.js`，四个预设：

- **Yuki（默认）** — 女大学生、活泼开朗、不黏人、不常生气
- **女友（黏人型）** — 长篇人设定，规定关系状态、说话方式、情绪互动与底线
- **学习助手（掩护模式）** — 正经工具口吻，防同事瞄屏
- **通用助手** — 中性

Yuki 的人设要点：把她当**朋友**而不是恋人。刻意写了「不追问『你为什么不回我』」
「有自己生活，聊天是分享不是索取」「他忙的时候说『那你先忙』就好」，
因为模型很容易把「陪聊女性角色」默认演成黏人女友。

所有人设都包含**反助手倾向**的约束，否则模型容易漂回客服腔：
不许自称 AI、不许总结式收尾（「希望以上对你有帮助」）、被问「你是不是 AI」时
不切换助手口吻。这类人设要写得具体，泛泛写「扮演我女友」效果很差。

### 立绘处理

源图（`resources/yuki/`）是 2048×2048 不透明 PNG，**文件名即动作**。
`scripts/prepare-yuki.js` 做四件事：

1. **抠背景**：从四个角 floodfill。**不能**用全局 `-transparent` ——
   实测 fuzz 20% 会把白衬衫和皮肤一起抠穿（脸都透明了）。
   背景色每张略有差异（`253,249,238` ~ `254,255,241`），所以每张单独采样。
2. **去水印**：右下角「豆包AI生成」颜色与背景几乎一致，floodfill 抠不掉；
   但它落在纯背景上，直接清空右下角矩形（实测包围盒 x 1691-2013, y 1937-2007）。
3. **裁白边并缩放**到高 300（UI 用）与 512（备份）。
4. **导出头像**：取「比心」那张的上半身裁成 128 方形（`AVATAR_SLUG` 可改）。

产物在 `resources/pet/`，UI 副本在 `src/renderer/public/`（调色板压缩到 14-22KB）。

### 表情系统

12 张立绘分两类（`PET_EXPRESSIONS`）：

**状态类**（由工作状态长期决定）

| key | 图 | 含义 |
|---|---|---|
| `work` | pose1 握拳 | 摸鱼进行中 |
| `happy` | pose2 蹦跳 | 已赚满 / 进度过半 |
| `rest` | pose3 眨眼 | 休息日 |
| `idle` | pose4 站姿 | 尚未开工 |

**表情类**（互动临时触发，配合台词结束自动恢复）

| key | 图 | 触发 |
|---|---|---|
| `shy` | 害羞捂脸 | 长按贴贴 |
| `angry` | 生气鼓腮 | 连点 4 次 |
| `think` | 思考歪头 | 挂机说话 / 对话中 |
| `sleep` | 抱膝睡觉 | 深夜 |
| `jump` | 双手上举 | 打卡成功（备选） |
| `heart` | 比心 | 悬停搭话 / 早上问候 |
| `surprise` | 睁大眼 | 双击 |
| `shrug` | 摊手叹气 | 拖拽放下 / 快下班 |
| `snack` | 吃零食 | 摸鱼中偶尔出现 / 挂机轮换 |
| `music` | 戴耳机 | 挂机轮换 |
| `coffee` | 递咖啡 | 久坐提醒 |
| `wave` | 挥手再见 | 退出前 |
| `yawn` | 打哈欠 | 深夜 / 早八，挂机轮换 |
| `thumbsup` | 竖大拇指 | 打卡成功 |

### 挂机姿态轮换

长时间显示同一张立绘会像静态图。`IDLE_POSES_BY_VOICE` 里的姿态会定期轮换，
而且**池子随亲密度解锁** —— 刚认识时只有 4 个动作，越熟越多：

| 档位 | 可用动作数 |
|---|---|
| 有点眼熟 | 4（snack / music / think / yawn） |
| 熟络起来了 | 5（+ coffee） |
| 好朋友 | 7（+ shrug / heart） |
| 默契搭档 | 9（+ surprise / shy） |
| 形影不离 | 10（+ sleep） |

为什么这样改：原来 18 张立绘里 **9 张只能靠手动互动触发**，不点就永远看不到，
其他图基本是废资源。现在挂机能自动轮到 14 张，剩下的 4 张是**语义上必须由事件触发**的：

| 图 | 触发 |
|---|---|
| `angry` | 连点 4 次 |
| `wave` | 退出前 |
| `thumbsup` | 打卡成功 |
| `jump` | 补卡成功（一次补齐多天） |

把这几个塞进挂机池会很突兀（没事突然竖大拇指？），所以不解锁。

解锁只增不减：高分档的池子一定包含低分档的全部动作，单测锁住了这条。

展示优先级：**互动表情 > 挂机姿态 > 状态心情**。
轮换时会跳过有台词/表情的时刻，不抢画面。

深夜和早八（`isTiredHour()`，即 23:00–09:00）只显示 `TIRED_POSES`
（yawn / sleep / think），不轮换吃零食这类精神头很足的动作——时间不匹配会出戏。
若过滤后池子为空会回落到完整池，不会卡住不轮换。

`EMOTE_FOR` 把「情境 key → 表情 key」的映射单独抽出来，改台词不影响表情逻辑，
也便于单测覆盖（`smoke.js` 会校验每个互动都配到了**实际存在**的图片文件）。

展示优先级：**表情类 > 状态类**，表情到期后自动回落到当前状态。
`say(text, emoteKey, holdMs)` 把台词和表情绑在一起说，调用方只需给一个 key。

### 排障：「测试连接成功但对话失败」

设置页有「全链路自检」按钮（`service.chatDiagnose()`），逐项跑并摊开结果：

```
✓ 读取设置       provider=deepseek model=deepseek-chat
✓ 配置校验       BaseURL=https://api.deepseek.com
✓ API Key       已填，长度 35，前缀 sk-2d…
✓ 非流式请求     model=deepseek-chat
✓ 流式请求       收到 2 字，model=deepseek-flash
✓ 流式增量回调   onDelta 触发，累计 2 字
✓ 数据库读写     写入并读回 2 条消息
```

关键在**「非流式」与「流式」是分开的两步**：`测试连接` 只发一次非流式短请求，
而真实对话走 SSE 长连接。若前者成功、后者失败，通常是网络中间设备（代理 / 公司防火墙 /
杀毒软件）拦截了 `text/event-stream`，这是最常见的「测试通过但不能对话」原因。

`chatDiagnose` 不落库、不改设置，可反复点。

### 为什么不用「网页版免费接口」

`chat.deepseek.com` 的网页接口需要从浏览器抠登录 Cookie，实测直接调用返回 **429**，
且官方随时可能改签名或封号，不适合做成产品功能。所以只走官方 API + 自填 Key。

## 窗口找回：任何情况下都不能「丢了就回不来」

桌宠、面板、对话窗都是 `hide()` 而不是销毁，所以它们**一直存在于任务栏之外的进程里**，
只是看不见。问题在于恢复入口本身有依赖：

| 入口 | 依赖 |
|---|---|
| 侧边栏「桌宠开关」 | 需要**面板窗口**开着 |
| 托盘菜单 | 需要**能找到托盘图标** |
| 右键菜单 | 需要**桌宠可见** |

如果桌宠和面板都关了，而托盘图标又没找到（Windows 11 默认把新图标收进溢出面板），
就真的没有入口了 —— 这正是「关了桌宠就找不回来」的原因。

修法：

1. **托盘图标改成能认出来的猫脸**。原来是个 10×10 纯色方块，缩到托盘尺寸后毫无辨识度；
   现在 32×32 画了耳朵和眼睛，缩略后仍能看出是猫。
2. **托盘单击走兜底逻辑**（`restoreAnyWindow()`）：有窗口可见才切面板，
   全隐藏就直接把桌宠叫回来，并弹一条提示。
3. **托盘菜单加「找回桌宠」/「全部显示」**。文案按真实可见性动态变化：
   窗口销毁显示「找回桌宠」，存活但隐藏显示「显示桌宠」，可见显示「隐藏桌宠」。
4. **托盘菜单在可见性变化时重建**（`show` / `hide` / `closed` 事件），
   否则文案会和实际状态脱节。
5. **侧边栏按钮如实反映状态**：可见显示 `🐱隐藏桌宠`，隐藏显示 `🐾显示桌宠` 并加虚线边框。
   之前文案固定为「桌宠开关」，点了没反应时用户会以为坏了。

托盘单击的语义是「我找不到界面了」，所以它**不做纯切换**——那样连点两下又回到原点。
只有确实有窗口可见时才当切换用。

## 缩放值必须单向来自设置

`petScale` 只能有一个真相来源：`settings.petScale`。渲染层用 **computed** 派生，
不要再存一份 `ref` —— 踩过的坑：

1. 早期用 `const scale = ref(1)` 只在 `onMounted` 赋值一次。设置页/托盘改了
   `petScale` 后，**立绘尺寸不会跟着变**，但主进程已经把窗口放大/缩小了。
   结果就是「窗口 340×700 里塞着一个 73×83 的立绘」——图只有该有的一半大，
   点击热区对不上，表现为**点他没反应**。
2. `pet:setScale` 改了窗口但**没广播状态**，桌宠要等 15 秒轮询才重排，
   这段时间内窗口和图是不同步的。
3. `settings:reset` 把 `petScale` 恢复成 1，但**没调用缩放的窗口调整**，
   于是 1× 的立绘留在放大后的窗口里。

现在三条路径（菜单按钮 / 设置滑块 / 重置设置）统一走 `applyPetScale()`，
并且在修改后广播状态。

排查这类问题的关键：**分别量窗口尺寸和 `.pet` 的元素尺寸**，两者应当
`340×700 : 118×136` 成比例；若窗口对而元素不对，就是 CSS 变量没更新。

## 桌宠拖拽：必须交给系统，不能自己 setPosition

桌宠移动用 `-webkit-app-region: drag`（见 `PetApp.vue` 的 `.pet`），**不要**改回
「监听 mousemove → 调 IPC → `win.setPosition()`」的写法。原因：

窗口一旦跟着指针移动，光标相对窗口的位置就在持续变化，Chromium 会在拖拽途中
停止派发 `mousemove`（实测第二次移动之后事件就断了），表现为「拖不动 / 拖一下
就卡死在原地」。这是自驱移动窗口的固有回授问题，加节流也治不好。

交给窗口管理器后事件不经过渲染进程，拖拽全程顺滑；代价是：

- 桌宠区域内的交互元素（菜单、气泡）必须显式设 `-webkit-app-region: no-drag`，
  否则点不到。
- 拖拽结束也会派发 `click`，需要一个位移标志区分「拖」和「点」。

位置由主进程监听窗口 `moved` 事件写入 `meta.petPosition`，重启后恢复；
恢复前会校验坐标是否落在当前显示器工作区内，避免换分辨率后桌宠跑到屏幕外。

## 节假日与调休

数据源 `timor.tech`（免费无 Key），**必须带 User-Agent**，否则返回
Cloudflare 验证页而不是 JSON。按年缓存进 `meta` 表，7 天有效；
联网失败用旧缓存，没缓存就退回「只看周末」——功能不因此不可用。

```js
isRestDay(settings, date, holidayTable)
// 有表时以表为准：
//   法定放假 -> 休息（哪怕周三）
//   调休补班 -> 上班（哪怕周日）   ← 关键
// 无表时退回 isWeekendRestDay()
```

**这个修复了一个真实 bug**：2026-09-20 是周日，但属于「中秋节前补班」。
只按星期判断会算成休息日、摸鱼收入变成 0，而实际那天要上班。

## 桌宠互动

`src/shared/interactions.js` 存台词池与选择逻辑，纯函数便于单测。

| 交互 | 行为 |
|---|---|
| 悬停 1.2s | 搭一句话 |
| 单击 | 回应；1.2s 内连点会累积，第 4 下开始抱怨「摸一次够啦」 |
| 双击 | 「诶诶诶，两下！」 |
| 长按 700ms | 贴贴，晃一晃 + 记 2 点亲密度 |
| 拖拽放下 | 「放我下来啦」 |
| 挂机 | 按设置间隔随机冒泡（区间打散，避免像定时机器人；间隔再乘亲密度倍率） |
| 久坐 | 工作中每 50 分钟提醒起身 |
| 情境 | 早上 / 刚上班 / 临近下班 / 下班 / 休息日各有台词，**每场景每天只说一次** |

所有台词都按当前亲密度档位从 `linesFor(key, voice)` 取，详见「亲密度」一节。

台词选择会避开上一句（`pickLine`），否则连续两次一样会很呆。

亲密度存在 `meta.affinity` 而不是 `settings`：它是累计计数器，
混进设置会让「重置设置」把互动记录一起清掉。

## 亲密度：数值必须变成行为，否则等于没有

亲密度有两层，缺一层就是个没用的数字：

**第一层 · 累计得点**（`AFFINITY_GAIN`）

| 来源 | 点数 |
|---|---|
| 聊天一条用户消息 | +2 |
| 一轮问答真正聊完 | +3 |
| 摸头 / 长按贴贴 | +2 |
| 双击 | +2 |
| 单击 | +1 |
| 每天见面 | +1 |

等级表 `AFFINITY_LEVELS` 复用「有点眼熟 → 熟络起来了 → 好朋友 → 默契搭档 → 形影不离」，
上限 300 点：**封顶是刻意的**。无限涨会让等级卡死在最后一档、进度条永远是满的，
数值本身反而失去意义。

**聊天另设日上限**（`CHAT_AFFINITY_DAILY_CAP = 60`）。不设的话一口气聊三十轮
就能从 0 冲到「好朋友」，等级推进完全没有节奏。手动互动（摸头/双击）不受这个上限约束。

**第二层 · 数值改变行为**（`AFFINITY_VOICE` + `linesFor`）

这是关键：只涨数字不改说话方式，用户感觉不到关系变近。

| 档位 | 行为变化 |
|---|---|
| 有点眼熟 | 主动说话频率 ×1.15（还很生疏，少打扰） |
| 熟络起来了 | 句首挂「诶，」前缀 |
| 好朋友 | 频率 ×0.9，挂机台词池追加「主动分享自己」的句子 |
| 默契搭档 | 频率 ×0.8，追加更懂你的句子 |
| 形影不离 | 频率 ×0.7，切专属台词池（不再说客套话） |

台词池不做「每档一套完整池子」——那要写五倍台词，写不细就会显得敷衍。
通用池上挂前缀，只有最高档才切专属池。

前缀会跳过语气词开头的句子：`诶嘿…` 加前缀会变成「诶，诶嘿…」。
这条规则有单测（`语气词句跳过前缀`）。

**连续性**：`lastDay` 管「连续互动天数」，断档重新计数。

**注意 API 形状**：service 暴露的是 `addAffinity(delta, opts)` 两参形式
（`now` 由内部注入），`opts.kind === 'chat'` 才计入聊天配额。
传错参数不会报错，只会静默漏记聊天配额 —— 单测覆盖了这条。

## 漏打补卡

打卡日历只能补「今天」，漏掉的历史工作日（比如入职后忘了打）需要一次性补齐。

```js
service.previewBackfill(fromKey, now)   // 只读，不写库
service.applyBackfill(fromKey, now)     // 批量写入
```

**口径与摸鱼收入完全一致**：复用 `isRestDay`，所以有节假日表时
法定假日跳过、调休补班日照常补；没有表只能按周末判断，界面上会提示这一点。
这样补出来的记录不会和「本月工作日」对不上。

两个实现细节：

- **先预览再写入**。补卡是不可逆的历史写入，界面上必须先把「会补哪几天」摊开确认。
- **`node:sqlite` 没有 `db.transaction()`**（那是 better-sqlite3 的 API，实测
  `db.transaction` 是 `undefined`），所以 `store.addCheckins` 手写
  `BEGIN`/`COMMIT`/`ROLLBACK`。50 天的补卡实测 7ms。

### 连续打卡按「工作日」连推

补卡暴露了一个老 bug：`store.streak()` 原来按**日历天**连推，
于是周五打了卡、周一再打卡，「连续」显示成 1 天 —— 用户明明没漏。

现在 `store.streak(todayKey, isRest)` 接收休息日判定：休息日**既不计入也不算断档**，
由 service 层按节假日表算好传进来（store 不碰日历规则）。
中间缺一个工作日仍然正常断档，单测两种情况都覆盖了。

## 挂机台词：角色必须如实传递

**症状**：她会对着自己说过的话发问。比如她说「我今天好累」，
过一会儿冒泡「你今天是不是很累呀？」

**根因**：把整段聊天记录拼成**一条 user 消息**喂进去：

```
[user] 最近的聊天记录：
       用户：你还没睡吗
       Yuki：我今天好累，改了一下午图
       用户：那你早点休息
[user] 请说一句和上面内容有关的话。
```

模型看到的是「**用户转述的**一段聊天」。它认不出哪句出自自己，
于是把自己说过的话当用户的来追问。文字前缀 `Yuki：` 骗不过模型的角色理解。

**修法**：按真实 role 重建多轮消息（`recentDialogueMessages`）：

```
[system   ] 【当前时间 — 必须严格遵守】…
[user     ] 你还没睡吗
[assistant] 我今天好累，改了一下午图
[user     ] 那你早点休息
[user     ] （以上是你和我的真实聊天。现在突然想起一件事…）
```

`assistant` 那轮在结构上就是她自己的话，模型不可能当成用户说的。
`CHATTER_SYSTEM_PROMPT` 里再显式说明一次 role 归属，双保险。

**为什么不用「转述文本 + 加一堆说明」**：模型对 role 的理解来自消息结构，
不来自正文里的标注。结构对了就不用解释，结构错了怎么解释都不可靠。

`recentDialogueText`（拼人看的文本）已删除 —— 它在生产路径上再无调用方，
留着只会诱使后来者又拼出那个 bug。

## 时间感：人设必须喂时间，否则她会自己编

**症状**：早上九点多，Yuki 说「我去吃午饭了」。

**原因**：人设里写了「食堂、早八、作业」这些生活场景，但模型**不知道现在几点**。
没有时间锚点，它只能从人设里随便挑一个场景 —— 于是时间线就乱了。

**修法**：每次请求都注入一段实时时间块（`timeContextFor`，在 `src/shared/moyu.js`），
拼在 system 提示词**最前面**（长上下文里模型对开头注意力更稳，而且要压过人设里的泛化描述）：

```
【当前时间 — 必须严格遵守】
现在是 2026 年 9 月 21 日 周一 09:10（上午）。
上午有课或者在做作业、改图。
你的生活节奏必须和这个时间对得上：不要提吃午饭、吃晚饭、下班、睡觉、晚安。
```

三个设计点：

1. **禁止项比许可项有效**。只给「现在是上午」模型仍会自由发挥，
   所以每个时段都显式列出「此刻不该说什么」。这和「反助手倾向」约束是同一个套路。
2. **时段按她的人设划分**（大学生作息，不是打工人的）：凌晨 / 清早 / 上午 / 中午 /
   午后 / 下午 / 傍晚 / 晚上 / 深夜，共 9 段。中午说「在食堂」合理，上午说就是 bug。
3. **带上用户的作息**。工作日告诉她「他在上班，别拉他出去玩」，
   休息日则「别问他工作上的事」—— 否则她会在工位上约你出去玩。

注入点覆盖全部三条请求路径：真实对话（`sendChat`）、挂机台词（`generateChatterLine`）、
全链路自检（`chatDiagnose`）。挂机台词尤其需要 —— 她主动冒泡时更容易随口说错时间段。

`runtime.withClock: false` 可关掉时间块（自检/测试用）。
时间块计入 `trimByChars` 的 `reserveChars` 预留，所以长历史裁剪时不会把它挤掉
（`chat-test.js` 有专门覆盖）。

## 服饰系统（和动作正交的第二个维度）

源素材里除了 18 张**动作**立绘，还有 17 张**服饰**立绘（便服/睡衣/旗袍/泳装/修女…）。
这两者是**正交维度**，不能混成一类：

- 动作决定「她在做什么」（摸鱼 / 睡觉 / 生气…）
- 服饰决定「她穿什么」（常服 / 睡衣 / 旗袍…）

每套衣服只有**一张**图（不是每个动作都有一套），所以服饰不能当动作立绘用——
那样换装后表情会全部失效。实际用法是三种：

1. **并入挂机轮换池**：她待着时不只是换动作，也会换身衣服
2. **对话窗旁的独立立绘小窗**：按时间自动换装
3. **手动换装**：桌宠右键菜单、对话框上方「👗 当前穿着」、立绘小窗、设置页，
   四处都写同一份设置

入口数量的坑：把立绘移到独立小窗时，对话框里那个 👗 一度被我改成
「显隐立绘窗」，**换装入口就这么无声丢了**（只剩「点小窗里的立绘」一条路）。
现在 👗 回到换装语义，显隐另给一个 🪟 按钮。
`smoke.js` 有一条守卫断言四个入口的写入路径都在 —— 实测移除任一入口会立刻失败。

#### 命名空间必须分开（踩过的坑）

`prepare-yuki.js` 原来有个兜底规则：文件名带 `(N)` 就映射成 `poseN`。
新素材里 `睡衣 (1).png` 因此被映射成 `pose1`，**正好撞上「握拳」**——
跑一次就会静默覆盖现有立绘（实测确认了冲突）。

现在服饰走独立命名空间 `outfit-<slug>`，动作走 `yuki-<slug>.png`，
两组互不相干。

#### 「同款多版本」是个错误假设

我一度以为是「同一套衣服的多个序号版本」，于是加了 `dedupeOutfits`：
按前缀归类 + 取序号最小的一张。**结果丢掉了 9 张有效素材。**

实际逐张比对（缩略指纹全不同、RMSE 6000~14000）并目视确认后：
`便服 (1)…(5)` 是**5 套不同的衣服**（白色针织裙 / 红外套制服 / 荷叶边裙 /
白上衣黑裙 / 深色制服），`睡衣 (1)…(5)` 同理（蕾丝睡裙 / 黑吊带袜 /
粉吊带 / 连体衣 / 短睡裙）。

所以现在改成**按完整文件名精确匹配**（`OUTFIT_FILES`），
一张图一个 slug，共 **17 套**。两条纪律：

- 不做任何形式的「同款合并」——判断相同不能靠命名习惯，必须看内容
- 遇到没登记的名字**直接报错中止**，不再静默丢弃（静默丢弃正是上次的根因）

#### 解锁与换装

服饰按亲密度分批解锁（和动作一样只增不减）：

| 档位 | 可用服饰 |
|---|---|
| 有点眼熟 | 无（刚认识不换装） |
| 熟络起来了 | 便服 |
| 好朋友 | + 红外套、荷边裙、居家清凉 |
| 默契搭档 | + 黑白裙、深色制服、吊带、长裙 |
| 形影不离 | 全部 17 套（含睡衣系列、旗袍、泳装、修女、cosplay） |

于是挂机候选池（10 动作 + 服饰）随关系增长：**4 → 5 → 12 → 16 → 27 项**。

时间自动换装规则刻意简单（换装是氛围，猜太细反而不合时宜）：

| 时段 | 穿着 |
|---|---|
| 23:00–07:00 | 睡衣 |
| 07:00–09:00 / 21:00–23:00 | 居家清凉 |
| 其余 | 便服 |

`outfitMode: 'auto' | 'fixed'` + `outfitSlug` 存在 settings 里，
所以桌宠菜单、对话窗、设置页三处读写的是**同一份**，改哪边都同步。

#### 「每个都会轮换用到」——深夜不能用硬过滤

深夜/早八（23:00–09:00）原本**排除**非困倦动作，只留 `TIRED_POSES`。
这在「让每张图都用上」的目标下是错的：那个时段占一天近 10 小时，
被排除的 7 项（snack / music / coffee / shrug / heart / surprise / shy）
等于半天都看不到 —— 满级池从 19 项掉到 12 项，最低档更是只剩 2 项。

现在改成**加权**（`weightedPool`，困倦项 ×4），仍然偶尔出现其他动作：

```
满级池 19 项 → 深夜仍是 19 项，只是 yawn/sleep/think 更频繁
```

`weightedPool` 用重复填充实现，而不是给 `pickLine` 加权参数 ——
后者会污染所有调用方，而这个需求只有轮换场景有。

单测里跑了「白天 2000 次 + 深夜 2000 次」的模拟，断言**每个不同项都被抽到过**
（`白天轮换覆盖全部项` / `深夜轮换也覆盖全部项`）。

#### 对话窗立绘必须放在窗外

对话框宽只有 420px，立绘浮在消息流右侧**必然压到文字**。
所以立绘是个**独立的无边框窗口**（`ChatPetApp` + `chatpet` 路由），
贴在对话框左侧；左边放不下会自动翻到右侧。

配套细节：

- 对话框 `move` / `resize` 时立绘窗跟着走，`closed` 时一并销毁（不留孤儿窗）
- `setFocusable(false)` —— 它只是装饰，抢焦点会打断打字
- 对话框内保留「👗 当前穿着」换装入口，显隐另给一个「🪟」按钮

## 手机端立绘：服饰与动作交替

19 张立绘分两个**正交维度**：

| 维度 | 数量 | 内容 |
|---|---|---|
| 服饰（`outfits/`） | 17 | 穿什么 |
| 动作（`poses/`） | 18 | 在干什么 |

桌面端一直两个都用了（动作按亲密度分 5 档），但手机端早期只上服饰 ——
18 个动作立绘全部闲置，她永远一个姿势，像张静态贴图。

现在顶部立绘在两者间**交替**（一张图没法同时表达两件事）：

- 相位按**分钟**翻转，配 30 秒定时器，保证到点就能看到变化
- 动作按 5 分钟一档轮换，避免每分钟跳一次太躁
- 只在页面可见时刷新（后台跑定时器是白耗电，回来时姿势突变也像 bug）
- 动作池按时间段选：深夜只有「打瞌睡/打哈欠」，
  不然会出现「穿着睡衣却在蹦跳」这种违和组合

## PWA 图标

由 `scripts/make-icons.js` 生成 —— 原来是手工产物、没有生成器，
换立绘或调构图都得手工重来，也没法复查上次怎么裁的。

**裁剪参数是调出来的，不是算出来的**：直觉做法是「按整张图居中裁剪」，
但那样**视觉上偏左**（她的脸偏画面左侧，右侧头发面积大，
几何中心 ≠ 视觉重心，用户一眼就看出来了）。现在的 `SIDE/LEFT/TOP`
是拿多个方案并排对比后定的，改之前请重新出对比图看一眼。

## 图鉴系统（装扮 17 套 + 视频 7 段）

聊天中自然解锁：聊到相关话题，她会主动发照片或视频给你。

### 触发刻意分三层，为省 token

```
① 条件解锁    亲密度 / 时段等硬条件   → 零成本，直接给
② 关键词预筛  本地字符串匹配          → 零成本，不命中就结束
③ 模型判断    只为「候选」调一次 API  → 唯一花钱的一步
```

三个省钱点：

- **已解锁的永不参与判断** —— 候选集合随进度变小，越用越省
- **关键词不命中就不调模型** —— 绝大多数轮次在 ② 就结束了
- **一次请求判断全部候选** —— 不是每个候选调一次

装扮和视频**共用同一份实现**（`checkGalleryUnlock` 按 `kind` 参数化）。
复制两套的话，改一处忘一处，就会出现「装扮省了 token 但视频忘了省」。

### 视频处理（scripts/prepare-video.js）

原片不能直接用，三个原因：

| 问题 | 处理 |
|---|---|
| `moov` 在 `mdat` 之后 → 手机要下完整个文件才能播 | `-movflags +faststart` 把索引前置 |
| 视频未加载时是空白块 | 抽首帧存 jpg 当 poster |
| 原片 0.7~2.0MB，7 段约 7.3MB | CRF 28 + AAC 96k，压到约 5.1MB |

中文源文件名（`摸头.mp4`）统一换成 slug（`headpat.mp4`）——
中文进 URL 要百分号编码且跨平台易出问题。

### 视频放在哪

- **`src/renderer/public/videos/`** 是唯一真相源，`resources/video/` 是原始素材
- 构建时复制到 `dist-mobile/videos/`
- **视频本体不进 SW 预缓存**：会拖慢首次安装。按需加载，解锁时下过一次自然缓存
- **封面图进预缓存**（约 60KB/张）：图鉴才能秒开

### iOS 上的音频

用户要求保留声音，而 **iOS 禁止带声自动播放**，所以视频带 `controls`
由用户主动点播放。关闭弹窗、切到照片时都会 `pause()` ——
否则声音会在后台继续放。

## 提示词顺序必须「稳定在前、易变在后」（省 50 倍）

DeepSeek 有**前缀缓存**：命中 $0.003/M，未命中 $0.15/M —— **差 50 倍**。
而前缀缓存是**从头逐字匹配**的，开头一变，后面全部重算。

```
✗ [时间块(300字)][人设(1560字)]
     ↑ 每分钟都在变 → 后面 1560 字人设每轮按全价重算

✓ [人设(1560字)][时间块(300字)]
     ↑ 稳定 → 命中缓存，只有末尾的时间块按全价
```

**实测证据**（同一人设，只改变化位置）：

| 情况 | cached | miss |
|---|---|---|
| 前缀不同 | **0** | 1003 |
| 前缀相同 | **768** | 234 |

所以代码里顺序是 `composeSystemPrompt(persona, clock)` ——
`chat.js` 里有一个专门的 helper 承载这条规则，避免有人散在几处改错。

**换序的代价与补偿**：时间块不再占开头，模型对它注意力略降。
实测出现过「23:40 被读成 11:40」。补偿办法是在时间块里**显式给出两种表述**：

```
现在是 2026 年 9 月 21 日 周一，**23:40（24 小时制）**，也就是深夜11:40。
```

加上时段词（深夜）后复测 5/5 全对。
`smoke.js` 有守卫断言顺序 + 24 小时制消歧，改回旧顺序会立刻失败。

## 她必须「知道自己知道时间」

**症状**：问她「现在几点/周几」，她含糊其辞或答错。

**先排除的假设**：注入路径一直是好的 —— 时间块每轮都在 system 最前面，
日期/星期/时刻都正确，长对话 30 轮后依然在。
所以问题不在「没给她时间」，而在**提示词没让她意识到自己知道**。

**原提示词的缺陷**：整段「时间感」只写「**不要**说什么」
（不要提早午饭、不要报时…），从没写过「**你确实知道现在几点**」。
再叠加「不要频繁报时」这条，模型很容易把时间块理解成
「约束我行为的背景设定」而不是「一个我可以说出来的事实」。

于是被问时间时，它会绕开或瞎猜。

**修法：把「时间感」从纯禁止改成主动认知**

```
- 系统会在对话开头给你「当前时间」，那是真实的此刻，不是设定、不是示例。
- 你确实知道现在是几点、周几、几号。被问到就直接照实说
  （「现在下午三点多啦」「都周一了」），不要含糊、不要反问、不要说自己不知道。
- ...
- 除了被问到、或话题自然带到，平时不用主动报时 —— 它是给你校准行为用的。
```

注入块同步改了措辞：标题从「必须严格遵守」改成「**这是真实的此刻**」，
并加一句「你确实知道现在的时间。如果有人问你几点、周几、几号，
照上面直接回答，不要含糊或反问」。

**实测（真实 API）**：

| 场景 | 回答 |
|---|---|
| 周一 14:15 问几点 | 「两点十五，下午。你那边刚上完课还是也在摸鱼？」 |
| 周一 14:15 问周几 | 「周一呀，下午两点多，正上课呢😩」 |
| 周一 07:30 | 「现在早上七点半啦，周一。这个点你怎么醒的，赶早八吗？」 |
| 周一 23:40 | 「周一，都快十二点了，23:40 啦。你还没睡？我是在赶明天要交的作业……」 |
| 周六 15:00 | 「下午三点啦，今天周六～」 |

**通用教训**：只写禁止项，模型会「回避」而不「掌握」。
涉及「她应该知道某个事实」时，必须正面声明她知道，
否则禁止项会被误读成「这个话题不能碰」。

## 多模态：让她看图

后端支持图片输入（`deepseek-flash` 原生多模态）。图片可以**选文件 / Ctrl+V 粘贴截图 / 拖拽**进来，
发送前用 canvas 压到长边 1280 再转 data URL。

### 三个必须遵守的服务端约束

来自 DeepSeek 官方 vision 文档，任何一条搞错都会 400 或产生隐性浪费：

1. **图片只能出现在 user 消息里**。放 system / assistant 直接 400。
   所以 `normalizeForRequest` 会把非 user 消息里的图剥掉。
2. **只有最后一条 user 消息保留图片**，历史图降级成 `[图片×1]` 文字占位。
   不这么做的话，每轮都重发所有历史图片（每张最多 1024 token），
   聊几轮就把上下文预算吃光，费用也跟着涨。
3. **格式按文件内容判定，不看扩展名**。所以校验只认 data URL 里的 MIME，
   不去猜文件名。

### 内容块形态

`content` 有两种合法形态，按有无图片自动选择：

```js
'你好'                                        // 纯文本：保持字符串
[{type:'text',text:'看图'},                   // 有图：块数组
 {type:'image_url',image_url:{url:'data:...'}}]
```

没图时**返回字符串而不是单元素数组**是刻意的：让绝大多数请求保持原样，
不给所有调用方（含第三方兼容接口）引入新格式。

落库时序列化成 `{"blocks":[...]}`，纯文本原样存字符串 ——
老数据零迁移，也不需要给表加列。读回时靠 `{"blocks"` 前缀快速判断，
避免每条消息都 `JSON.parse`。

### 字符预算要特殊处理

图片是几百 KB 的 base64，按真实长度算会**瞬间吃满预算**；
但它的 token 成本实打实存在（每张最多 1024）。
所以 `contentCost` 给每张图记一个固定的 2000 字符占位 ——
既不能按原始长度算，也不能当零成本。

### 模型必须支持视觉

`deepseek-chat` 是纯文本模型，发图会 400。与其让用户对着含义模糊的上游报错发懵，
不如发送前拦住并说清怎么改：

```
deepseek-chat 不支持图片，请在「设置 → AI 对话」把模型换成 deepseek-flash
```

判断用**黑名单**（`NON_VISION_MODELS`）而不是白名单：
自定义服务商很可能提供视觉模型（如 `qwen2.5-vl`），白名单会误伤。

这个检查在渲染层也做一次（`onSend` 里），**在清空输入框之前** ——
否则用户打的字和图都丢了，还得重新弄一遍。

## 让她认识自己

**症状**：把她的立绘发给她，她说「这是一位棕发少女」——把自己当陌生人。

**原因**：她从来没见过自己。人设里只写了她是「女大学生」，
没有任何外形信息；而且即使写了文字，模型对自己长相的理解仍然很飘。

**修法：两条路一起走**，缺一条效果都不够稳。

### 1. 人设里的 `【你的样子】`

```
- 棕色长卷发，齐刘海，发量偏多，发尾微卷
- 红棕色的眼睛，皮肤白
- 常穿：白色针织连衣裙、白上衣配黑短裙、红色外套…
```

纯文字，零 token 成本（就几十字）。

**必须同时写「不像就不是我」的否认规则**：只教她认自己，
模型容易变成硬认 —— 别人发张网图也说「这是我」。

### 2. 参考图注入（`withSelfPortrait`）

给一张真实立绘，让她用视觉能力**亲眼看过自己一次**。请求长这样：

```
[system]    人设（含【你的样子】文字描述）
[user]      [自己的立绘] + 「上面画的**就是你**，记住自己的样子」
[assistant] 嗯，记住了，这是我。
[user]      用户的图片 ← 现在她能认出这是自己
```

三个关键设计：

1. **图片只能放 user 消息**（官方 vision 硬约束），所以套成 user/assistant 一对。
2. **配一句 assistant 回执**。只放一条孤立的 user 图 + 说明，容易被模型
   当成「待处理任务」；有来有回才像自然的对话历史。
3. **注入在 `trimByChars` 之后**。反了的话参考图会被当成最早的历史裁掉 ——
   白花 token 还没效果。

**成本**：每轮约 +1024 token（图片上限）。可接受，但也因此只在
模型支持视觉时注入 —— 纯文本模型收到图会直接 400，
所以 `deepseek-chat` 下自动跳过（那时退化成人设里的文字描述）。

参考图用哪张由 `SELF_PORTRAIT_SLUG` 决定（默认 `pose4` 正面站姿最清晰），
文件从 `dist/yuki-<slug>.png` 读，缓存一次后复用。

**路径解析放在主进程**（`loadSelfPortrait` 注入给 service）：
资源路径依赖打包方式（开发时在 `src/renderer/public`，打包后复制到 `dist/` 进 asar），
而 service 刻意不感知这些。读不到就返回空串 —— 没有参考图也能正常聊。

## 挂机冒泡的来源：两种内容混着说

自动说话有**两个来源**，按 6:4 随机选用，而不是「模型优先、失败才用台词库」：

| 来源 | 内容 | 权重 |
|---|---|---|
| `history` | 结合**最近两天**的聊天现编一句 | 0.6 |
| `pool` | `linesFor('idle', voice)` 台词库 | 0.4 |

只用一个都不行：全用模型会飘（而且没配 Key 时完全没话说），
全用台词库又和你们的实际聊天脱节。

**连续两次同源会被错开**：连着追问聊天内容有压力，连着说通用台词像复读机。
用 `lastChatterKind` 记住上一次的来源，命名上刻意区分于「生成失败回落」。

### 为什么限定「最近两天」

原先只按**条数**取（24 条），聊得少时会把几周前的内容捞出来，
她照着老话题搭话很出戏。现在是**时间下界 + 条数上限**叠加：

```js
const since = Date.now() - CHATTER_WINDOW_MS   // 2 天
const history = store.messagesSince(latest.id, since, 200)
```

两个都不能省：时间界定「多久之前算旧事」，条数防止两天内聊了几百条撑爆上下文。
两天也是刻意选的——够覆盖「昨天聊到一半的话题」，又不会拉回一周前。

两天内没聊过时返回 `ok: false`，由调用方用台词库——让她对着一周前的旧事搭话，
比说一句通用台词更奇怪。

## 自定义人设

内置人设写死在 `CHAT_PERSONAS`，用户自建的存 `personas` 表。

- 「复制」会连提示词一起复制成可编辑副本，并自动切过去
- 删除正在使用的人设会回落到默认，不会让人设变成空白
- `resolveChatConfig(settings, customPersonas)` **必须带上自定义列表**，
  否则自定义人设会被静默忽略、回落成 Yuki

## 桌宠窗口尺寸约束

右键菜单、气泡、桌宠三者是**同一个无边框窗口内的 flex 列布局**（菜单在文档流里，
不是 `position: absolute`）。窗口尺寸 `PET_SIZE` 必须同时容纳三者，否则菜单会被窗口
上边界裁掉——早期版本用 220×260，菜单只能看见下半截（打卡和打开面板直接不可见）。
当前为 **340×700**（菜单加了亲密度面板后内容约 420px，560 高会出现不易察觉的滚动条）；
`petScale` 会同步缩放窗口并保持右下角锚定。

菜单本身带 `overflow-y: auto` 兜底：万一以后加项导致超长，它会自己滚动而不是把桌宠顶出窗口。

## 摸鱼收入算法

```
日薪      = 月薪 / 本月工作日数
计薪时长  = (下班 - 上班) - 每日休息时长
已计薪    = clamp(现在 - 上班, 0, 在岗时长) × 计薪时长 / 在岗时长
今日收入  = 日薪 × 已计薪 / 计薪时长
```

- **本月工作日数按真实日历数**，不用固定的「双休 8 天」这类套餐值——2025-06 双休实际是 21 个工作日，套餐值会算成 22，日薪整体偏低约 5%。
- 休息日（双休/单休/大小周/不定休）当天收入恒为 0。
- 状态机：`尚未开工` → `摸鱼进行中` → `今日已赚满`，休息日走 `今日休息`。

## 数据与同步

本地表全部带 `id / updatedAt / deletedAt / syncState`：

```sql
checkins(id, dateKey UNIQUE, createdAt, note, updatedAt, deletedAt, syncState)
worklogs(id, dateKey, minutes, kind, createdAt, updatedAt, deletedAt, syncState)
settings(key, value, updatedAt, syncState)
events(id, type, payload, createdAt)
meta(key, value)
chat_sessions(id, title, createdAt, updatedAt, deletedAt, syncState)
chat_messages(id, sessionId, role, content, model, error, createdAt, updatedAt, deletedAt, syncState)
```

补卡写入的 `checkins.note` 为「补卡」，和现场打卡区分开。

`meta` 里存了几个跨表状态：`affinity`（亲密度与聊天配额计数）、
`holiday-<year>`（按年缓存的节假日表）、`petPosition`（桌宠位置）。

云端接入时只需：`pendingChanges()` 取增量 → 推送 → `markSynced(ids)`。
不需要改表结构，也不影响离线使用。

数据库落在 `%APPDATA%\desk-pet\desk-pet.db`。

## 安全边界
