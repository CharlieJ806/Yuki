## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 壳 | Electron 38 + Tauri 2 | 双壳同构：同一份 JS 业务层跑两壳（Tauri 化历程见 TAURI_MIGRATION.md） |
| 渲染 | Vue 3 + Vite 6 | 单份构建产物按 `?route=pet|panel|chat|chatpet|petmenu` 挂载五个应用 |
| 存储 | Electron：`node:sqlite` / Tauri：rusqlite 桥 | 两壳共用表结构（自带同步字段）；service 层全异步以兼容双后端 |
| 图形 | PNG 立绘 + CSS 动效 | 透明立绘按状态切换，无 3D、无骨骼 |
| 打包 | @electron/packager / tauri build | 免安装单文件 exe（两壳各自出包） |

> Electron 必须 ≥ 37（Node 22+，`node:sqlite` 所需）——该要求只约束 Electron 壳；Tauri 壳走 rusqlite。

## 桌宠动画（2D 可动关节）

桌宠是**纯 2D**：`<img>` 切透明立绘 PNG，没有 3D、没有骨骼。
想要「动起来」有两个层次，成本差一个数量级，见下。

### 现状：动作与服饰是两个正交维度

素材只有**整张立绘**（`resources/yuki-new/*.png` → `split-sheet.js` 切格
→ `install-pet-assets.js` 缩放分发 → `src/renderer/public/yuki-<slug>.png`）。
当前靠**换图**表达姿势：

- **动作** 24 张（挥手 / 打哈欠 / 睡觉 / 看书 / 抱膝哭…）→ `PET_EXPRESSIONS`
- **服饰** 24 套（JK / 睡衣 / 旗袍 / 圣诞装…）→ `OUTFITS`

两者正交，不能混成一类 —— 服饰图只有一张，当动作图用会让表情全失效
（这条在 `interactions.js` 里写死了理由，别改回去）。
对话窗旁小立绘的「此刻穿哪套」走 `outfitForTime` —— **已解锁服饰池 +
时间片哈希**（`OUTFIT_SLOT_MS = 30 分钟`），**不看时段**（时段适配表已删，
见「服饰系统」章），桌宠则是动作与服饰**同池**按可配间隔轮换 —— 见
「轮换：从『随机插曲』升级成『可配的定时刻拍』」。

**轮换节奏**（`PetApp.vue` 的 `rotateIdlePose`）：间隔由设置项
`petRotateMin` 定（默认 10 分钟，范围 1~180），实际等待叠 ±25% 抖动；
到点换一项，**换到动作或换到衣服一视同仁**，中间没有空档。
早期是「展示 20~40 秒 + 空档 40~100 秒」（约 60~100 秒换一次，
且空档期回落到站姿），那时服饰只是池里的一个随机项，看着像「偶尔换了件衣服」，
而不是「每隔一段时间换一套」——这正是用户后来提需求的原因。

### 已排除的路线：3D

试过 Meshy 图生3D + 自动绑骨 + 动画（三个独立计费 API，26 信用）。
**结论是不做**，原因是素材与玩法都不匹配：

- 现有 44 个 slug 是**独立整图**，3D 化后姿势必须改骨骼动画状态机，
  换装要从「换 PNG」升级成「材质/UV 切换」或准备 20 套模型 —— 数周工作量
- 桌宠常驻悬浮，3D 要持续占 GPU；实测 1.7 万面 34fps 尚可，
  但 Meshy 默认产出的 120 万面模型直接拖死核显
- 对话窗侧边立绘与手机端本来就该是 2D，3D 只惠及桌宠一个窗口

相关代码（`Pet3DViewer.vue` / `Pet3DLabView.vue` / `meshy-pet.js` /
`dev-3d.js` / `make-test-glb.js` / `three` / `undici` 依赖）已全部移除。

### 技术路线调研（2D 可动关节，2026-09）

想让桌宠从「换图」升级到「真的在动」，四条路线，**成本差一个数量级**。
前提约束：素材是**整张扁平 PNG**（44 个 slug，主体 179×300 级），不是分层 PSD；
桌宠是常驻透明置顶窗，**CPU 必须低**。

| 路线 | 需分层素材 | 能做到 | 工作量 | 许可风险 |
|---|---|---|---|---|
| **a. CSS 程序化动效** | 否 | 呼吸缩放、摇摆、浮动、眨眼叠加 | 极低（1–3 天） | 无 |
| **b. 顶点网格变形** | 否（整图贴网格） | 转头、躯干摆动、局部拉伸 | 中（1–2 周） | 无 |
| **c. 完整骨骼动画** | **是（硬前提）** | 四肢独立运动 | 高（44 套分层 + rig） | 视运行时 |
| **d. 视频/序列帧** | 否 | 固定演出，不可实时驱动 | 极低 | 无 |

现状：**只用 a**。`PetApp.vue` 对 `.pet-img` 施加
`@keyframes snuggle / bounce / bob / sway / breath / breathe-idle / wag`，
全部只动 `transform`（命中 Chromium 合成层快路径，常驻成本近零）。

> d 路线一度用于图鉴里的「解锁视频」，后来整体移除了 ——
> 视频素材体积大、且需要用户在聊天中解锁才有机会看到，
> 性价比不如照片。若将来要做固定演出可直接捡回这条路线。

#### 推荐：先做 a+，不必碰骨骼

**先榨干 CSS 路线的余量**，它已经能覆盖大部分观感需求：

1. **眨眼** —— 不需要新分层素材。`resources/yuki/眨眼.png`（→ `pose3`）已存在，
   把闭眼区域裁成小贴片，用 `clip-path` 遮罩在眼部叠一层，定时闪现即可。
2. **呼吸加形变** —— 现在只做 `translateY`，可加轻微 `scale` 与头肩反向位移，
   比纯位移更「活」。
3. **视线跟随** —— 鼠标靠近时对整图做小幅 `rotate`/`skew`，模拟转头。

若仍不满足，再上**路线 b**：把整图贴到 2D 网格（约 6×10 顶点）做局部形变。
PixiJS v8 的 `MeshPlane`/`PerspectiveMesh`（MIT）是现成的 WebGL 底座，
只需一次性为每张图标定控制点。**注意动态 import**，别让 PixiJS 进桌宠初始包
（3D 那次的教训：three 静态引入变成 592KB `three…`）。

#### 路线 c 的运行时选型（前提是愿意投入分层）

**真正的瓶颈不是运行时，是素材分层。** 44 套整图要拆成头/身/手臂/腿，
被遮挡区域还得 inpainting 补绘 —— 这是重资产投入，与选哪个运行时无关。

| 运行时 | 许可 | 结论 |
|---|---|---|
| **Rive** | runtime **MIT**，可离线 | ✅ 唯一「无发布闸门」的成品级选择。代价：导出 `.riv` 需 Cadet $9/月（2025-10 起） |
| **Live2D** | Core 闭源专有 | ⚠️ 可用。个人/小规模（年销 <1000 万日元）**豁免签约付费**；但**不能把 Core 连同项目一起开源发布**，且**不许做成「用户可导入任意模型」的容器**（Expandable Application 例外） |
| **Inochi2D** | BSD-2 | ⚠️ 理念正确、许可干净，但生态小、须用其 Creator 分层 |
| **Spine** | **非开源**，自定义许可 | ❌ 明文要求「每个集成者自持付费 Editor」。网上说「spine-ts 是 MIT」是**错的** |
| **DragonBones** | MIT | ❌ 编辑器停更（runtime 最后 push 2026-01），新项目不宜 |
| **Godot Skeleton2D** | MIT | ❌ 架构不成立：等于再跑一个引擎进程，与低 CPU 常驻冲突 |

#### 自动分层（把整图变成可用分层）

| 方案 | 状态 |
|---|---|
| **See-through**（[arXiv 2602.03749](https://arxiv.org/html/2602.03749v1)，Apache-2.0，4k★） | 唯一端到端开源方案：单张立绘 → 最多 23 个语义层 + 遮挡区 inpainting + 绘制顺序 → 分层 PSD。**但需 12–16GB 显存**（8GB 可 4-bit 量化），且面向 1080p+ 输入 —— 本项目 179×300 的小图会显著劣化 |
| SAM2 / rembg / U2Net | 只出前景 mask 或粗语义，**不补遮挡区**。旋转手臂会露洞，单用不够 |
| LaMa / MAT / SD-inpainting | 能补遮挡，但**需人工画 mask**，不是自动的（是 See-through 的内部组件） |

**结论**：自动分层是研究级、需 GPU + 人工精修，不能无人值守。
若要上路线 c，建议**先拿 1 张图跑 See-through 验证**，再决定是否扩到全套。

### 无头验证桌宠窗

桌宠是透明置顶无边框窗，肉眼不易核对渲染是否正确。主进程留了一个开关：

```bash
DESK_DEBUG_PORT=9222 npm run dev      # 然后 curl 127.0.0.1:9222/json/list
```

拿到 CDP 端点后可以量取窗口位置、派发鼠标事件、截图。
默认关闭，只有显式设了环境变量才生效。

> **踩过的坑：`ELECTRON_RUN_AS_NODE=1` 会让 Electron 退化成纯 Node。**
> 某些宿主环境（例如某些 IDE / agent 运行时）会把这个变量注进会话，
> 此时**任何 Electron 应用都起不来** —— 主进程以 Node 身份加载，
> `import { BrowserWindow } from 'electron'` 直接抛
> `does not provide an export named 'BrowserWindow'`，进程一秒内退出。
>
> 症状极具误导性：打包好的 exe 双击明明能跑，从那个会话里启动就「闪退」，
> 很容易误判成「构建坏了」。
>
> 对策是在启动前清掉它（子进程继承的是清掉之后的环境）：
>
> ```powershell
> Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
> ```
>
> 配好之后 `DESK_DEBUG_PORT` 与 `node scripts/open-mobile.js --debug`
> 都能用，可以真正**在运行中的页面上量数字、截图** ——
> 比例、滚动、层叠这类问题不该靠读代码猜（本文档里
> 「聊天背景的比例坑」就是靠 CDP 实测定位的）。

## 手机版（PWA）

桌面版之外还有一个**手机版**，在 `mobile/`。两端**各自独立运行**：
手机不依赖电脑开机，数据存在手机本地。

```bash
node mobile/build.js     # 产出 dist-mobile/，上传到你的域名即可
node mobile/serve.js     # 或本地预览：手机连同一 WiFi 打开 http://<电脑IP>:8899
```

**共享逻辑、独立数据**：

```
mobile/chat.js ──▶ ../src/shared/{moyu,content,interactions,gallery,
                     photoStories,photoMessage,tapLines,outfitStories,…}.js  ← 零复制
```

改桌面端的人设或时段表，手机端重新 build 就同步生效。
但对话记录和亲密度各存各的 —— 这是「互不依赖」的代价。

**为什么手机端不需要后端**：实测 DeepSeek 接口会回 CORS 头
（`access-control-allow-origin` 回显 Origin，`allow-headers` 含 authorization），
所以浏览器可以直连，不需要中转服务器。有些 API 不返回这些头，那种就必须中转。

**手机端没有的**：桌宠悬浮窗、挂机冒泡、打卡、摸鱼统计 ——
都依赖桌面环境（透明置顶窗口、常驻进程），移动 OS 不支持。

### 手机端的两处独有交互

1. **关键词动作**：她打字时输入框内容命中关键词就临时换立绘（5 秒后回常态）。
   规则表在 `shared/interactions.js` 的 `CHAT_ACTION_RULES`，
   两端共用同一份 —— 同一句话在两端的反应必须一致。
   挂在 `input` 事件而不是 `send` 上：没配 API Key 时发送是禁用的，
   挂 send 会导致「打了字却毫无反应」。带 20 秒冷却防连发抖动。
2. **聊天背景**：图鉴里点开一张照片 → 详情页里「设为背景」或「加入轮换」。
   三种模式（`chatBgMode`）：不设 / 固定一张 / 自动轮换。
   轮换池要**手动勾选**（`chatBgPool`）—— 她发来的照片里有不少是
   室内随手拍，未必都想当背景。间隔在设置里选（最短 5 分钟）。
   透明度 `chatBgOpacity` 默认 0.25。
   背景用 `::before` 遮罩压暗而非直接改图片 opacity ——
   照片明暗不均，不压暗气泡文字会糊。

   轮换的选图是**按时间片取模**算的（`shared/chatBackground.js`），
   不存「轮到第几张」——无状态，两端算出的一致，刷新也不会跳回第一张。

细节见 `mobile/README.md`。

## 打包产物

`npm run pack` 产出（两种形态，同一次打包的同一份内容）：

```
release/                          ← 交付区
  摸鱼桌宠-win32-x64/
    摸鱼桌宠.exe                  **双击即用**（主要形态，不必先解压）
    resources/ *.dll / locales/   Electron 运行时与应用
  electron/
    desk-pet-electron-<版本>-win-x64-portable.zip   绿色版压缩包（分发/传输用）
    desk-pet-electron-setup-<版本>.exe              安装器（npm run pack:installer）
  tauri/                         Tauri 侧产物（npm run pack:collect 归集）

```

**散装目录是主要交付形态** —— 用户拿到就能双击 `摸鱼桌宠.exe`，不用先解压；
zip 是它的压缩版，两者内容一致（zip 从交付区的目录压缩，不是从暂存区，
所以不会出现「zip 是旧的」）。

中间产物在 `.tmp-release/`（项目根、gitignored）：`installer.nsi` 要从那里取文件，
且它绝不能出现在交付区，否则就是「边交付边消失」。

`build.js` 只删**确定已被取代**的东西（`使用说明.txt` 旧文件名、
已迁走的 `手机端启动器-win32-x64/`）。**不用白名单**：白名单要求穷举
「所有合法产物」，改布局时会把当前正在用的产物误删 —— 上一版正是这么
把散装目录当成「旧布局」清掉的，而它恰是最常用的双击入口。

**exe 不能单独拷出目录**：Electron 在 exe 同目录找 `resources/`，
脱离文件夹会直接退出。所以「绿色版」是**整个文件夹**，不是单个文件。

手机端启动器是**本地便利产物**（双击起静态服务器看 PWA），
不随 Release 上传，落在项目根的 `release-mobile/`。

### 打包踩到的三个 Windows 坑（已在 build.js 里处理）

1. **`TEMP` 指向网络盘** → packager 的 rename 直接 EPERM。脚本把 `TEMP`/`TMP`
   强制指向本地 `%LOCALAPPDATA%\Temp\deskbuild`，并先在本地打包、再整体复制到 `release/`。
2. **Windows Defender 锁住刚解压的 `electron.exe`** → packager 收尾要 `rename` 解压目录，
   正好撞上扫描锁，稳定失败。脚本挂 `afterExtract` 钩子，反复「试 rename 再改回」
   直到锁释放（实测约 9s）再交给 packager 收尾。
3. **旧版程序还在运行** → exe / asar 被占用，清理 `release/` 时 `rmSync` 抛 EPERM。
   用户看到的是一段原始堆栈，完全看不出「程序没退出」这个真正原因。
   现在 `removeOutDir` 会把 EPERM/EBUSY 翻译成人话，并列出占用进程的 PID 与名字：

   ```
   ✗ 无法清理旧产物：<项目根>\.tmp-release\desk-pet-win-x64
     目录被占用，最常见的原因是「摸鱼桌宠」还在运行。

     检测到正在运行的相关进程：
       · PID 7872  摸鱼桌宠
       ...

     请先退出程序（右键桌宠 → 退出摸鱼桌宠，或托盘图标右键 → 退出），再重新运行 npm run pack。
   ```

   查进程走 PowerShell `Get-Process`，两个已踩过的坑写在 `listAppProcesses` 的注释里：
   必须显式设 `[Console]::OutputEncoding = UTF8`（否则中文进程名按 GBK 输出，
   Node 解出来是 `��������`）；语句间要用换行而非 `;`（`;` 会让 `|` 只作用于后半句，
   `ConvertTo-Json` 落空、退回表格输出，解析失败表现为「检测不到任何进程」）。
   查不到进程不影响打包 —— 整段逻辑失败即返回空数组。

另外 `tmpdir: false` 用于避开「`mkdtemp` 之后 rename 到已存在目录」这一在 Windows 上
必失败的动作。

## AI 对话

后端是 **OpenAI 兼容的 `/chat/completions`**（`src/main/chat.js`），用 Node 内置 fetch，
不引第三方 SDK。支持：

- **流式 SSE**：自己写的解析器（`parseSSE`），按 `\n` 切行累积 buffer，
  能正确处理「JSON 被 chunk 边界切断」和「多个 data 事件粘在一个 chunk」两种情况——这两种
  在真实网络下都会发生，是流式解析最常见的 bug 来源，`scripts/chat-test.js` 专门覆盖。
- **取消**：`AbortController` 按 `requestId` 存在 service 的 Map 里。
  注意 abort 可能发生在 `fetch()` 阶段**或**后续读取流的阶段，后者抛的是原生 `AbortError`，
  必须在读取循环外面 catch 并归一成 `ChatError(kind:'aborted')`，否则前端拿不到统一类型。
- **错误翻译**：401/402/404/429 等状态码翻译成中文，并尽量提取上游 `error.message`。
- **上下文**：只取最近 N 条**且排除 `error=1` 的消息**，避免把报错文本当成对话历史喂回去。

配置存在 `settings` 表（`chatBaseUrl` / `chatApiKey` / `chatModel` 等），
`chatApiKey` 只落本地库，不下发到渲染进程（`chatStatus()` 只返回 `hasApiKey` 布尔值）。
注意 `chatPersona` / `outfitMode` / `outfitSlug` / `petStories` 这几项是**逐会话**的
（每个会话是独立的她），存在 meta 的 `set:<key>:<sessionId>` 键下，不在 settings 表。

### 自动换装：从「时段适配」改成「池子里随机」

早先 `outfitForTime` 按 `OUTFIT_DAY_PARTS` 的时段适配表挑 —— 深夜穿睡衣、
白天穿常服，理由是「符合生活逻辑」且能命中「刚好穿着某套」这类解锁条件。

**用户后来明确要求去掉**：「不要跟随时间那个了，改成池子里随机」。
于是那张表和适配逻辑一起删了，函数仍叫 `outfitForTime`（改名要动 6 个调用点，
收益只是名字好看，不值得；行为已在函数头注释里写清）。

**但不能直接用 `Math.random()`。** 这个函数是在 **computed 里调用的**
（`currentOutfitSlug`），每次依赖变化都重算 —— 直接随机会让立绘和标签
在重渲染时乱闪（同一秒内换好几套）。

所以用**时间片哈希**：`floor(now / 片长)` 散列取模。同一片内恒定、跨片才换，
无状态、可重现 —— 与 `chatBackground.js` 的轮换是同一个思路。

片长 `OUTFIT_SLOT_MS = 30 分钟`，比桌宠立绘轮换（`petRotateMin`，默认 10 分钟）长：
这是「她今天穿什么」，不是「她现在在干嘛」。

smoke 里三条断言把新语义钉住：**同一片内稳定**（防有人改用 `Math.random()`）、
**跨片会变**（防退化成恒同一套）、**没有时段偏向**（把所有时段扫一遍应出现多套 ——
若哪天有人把时段适配加回来，凌晨那批会退化成睡衣，这条就红）。

> 注意「桌宠立绘轮换」和「她穿着什么」是两套东西：
> 前者是 `PetApp` 的挂机池（动作 + 服饰混在一起，`petRotateMin` 控制），
> 后者是这个函数（决定自动模式下的「当前穿着」，供菜单标签与小立绘用）。
> 用户这次要改的是**后者**。

### 一次生成、分多条发出

真人不会把三段话塞进一个气泡。她在**一次生成**里用 `<<<MSG>>>` 分段，
服务端按标记拆成多条落库、时间戳按固定间隔递增（`REPLY_SEGMENT_GAP_MS = 1200`），
渲染层已有的错峰队列就按相邻差值让它们一条条冒出来 —— **复用照片连发那套机制**。

四条纪律：

- **有标记时只认标记；没有标记时退而认「空行」。** `<<<MSG>>>` 是自造 token，
  实测模型更爱用空行分段（`A\n\nB`），旧实现只认标记的表现是
  「一个气泡里塞了两句」。空行方案的条件全是**收紧**方向的：
  含 ``` 围栏不切、单换行 `\n` 不算、每段都要 ≥ `MIN_IMPLICIT_SEGMENT_CHARS`
  个字、切不出 2 段就原样返回整条 —— 宁可少切一个气泡，不可切错。
  （阈值取 6 不取 8：实测样本第二段「刚顺手看了个猫」恰好 7 个字，
  取 8 会漏掉这条最典型的 case，等于没修。模型不听话、或用户用自定义人设
  没写这条指令时，没有空行的回复行为与以前完全一样。）
- **间隔必须落在错峰窗口内**（渲染层 `STAGGER_MAX_MS = 3000`）。
  超过 3000 会被判成「普通对话」立即显示，节奏就没了。
- **流式预览只显示第一条**（`livePreviewOf` 截到第一个标记）。不截的话
  生成过程中用户会在气泡里看到 `甲<<<MSG>>>乙` 这种原始文本，标记直接暴露，
  生成完又重排一次，观感很跳。
  （已知残留：空行分段只在生成结束、落库时才生效，流式过程中那一整条原文
  仍会先完整显示，然后「啪」地重排 —— 与标记方案的观感差距在 `livePreviewOf`。）
- 上限 **4 个气泡**，防止刷屏；**超出的内容并进最后一条，不许丢**。
  旧实现是 `parts.slice(0, max)`：模型发 5 段以上时第 5 段起既不显示、
  也不落库（service 落的库就是这个数组），往上翻也找不回 —— 静默丢内容。

**踩过的坑**：人设写在 `moyu.js` 的**模板字符串**里，我在指令示例中用了反引号
（`` `<<<MSG>>>` ``），直接把模板字符串闭合了 → 构建报语法错误。
提示词里要引用标记就别加反引号。

### 未读：按「她说的、晚于已读位置」算

普通回复和**主动找话题**（`generateTopicLine`，落成真消息那条）**共用同一套语义** ——
不给主动消息单独打标记，那种做法会让两套未读逻辑各自漂移。

**「主动说话」不在此列**：`generateChatterLine` 只在桌宠气泡里冒一句，
**不入库、不产生未读**（说完就没，下一节有分工表）。
所以「搭话之后要 `emit('unread', ...)`」说的是主动找话题与普通回复，
主动说话没有这一步。

- 已读位置按会话存在 `meta` 的 scoped 键（与图鉴/亲密度同一套命名空间约定）
- 对话窗获得焦点/重新可见时 `markChatRead()` 打点
- **已读位置取「最新消息的时间戳」，不是 `Date.now()`**：
  多段回复的时间戳是 `now + i×间隔` 提前写好的（未来时间），
  用 now 会让它们被判成「还没发生」而继续算未读 ——
  表现是「点开对话窗红点也不消失」。这条有专门的单测。
- 反复打点取 `max`，不回退（多窗口竞争）

**推送要用轻量事件**：回复/搭话之后发 `emit('unread', ...)`，
而不是 `emit('state', ...)` —— 后者要载 11 年节假日表 + 算薪资。
实测不推的后果：已经聊完 3 条，桌宠红点还停在上一轮的 7（要等 15 秒轮询）。

### 主动说话不入库、主动找话题才入库

这是**两个刻意拆开的功能**（用户明确要求），共用同一份「最近两天对话」上下文
与 `sanitizeChatter` 清洗，区别只在提示词与**是否落库**：

| 函数 | 形态 | 落库 | 未读红点 | 设置项（默认） |
|---|---|---|---|---|
| `generateChatterLine` | 桌宠气泡里随口一句（自言自语） | **否** | 无 | `petChatterInterval`（12 分钟） |
| `generateTopicLine` | 真消息 | **是** | 有 | `petTopicMin`（60 分钟；设 0 = 关掉） |

- **主动说话**（气泡）不入库：气泡一消失就再也找不回来 —— 这是有意的
  「氛围」定位，不该污染聊天记录，也不该把红点点亮。
- **主动找话题**要入库：它得成为**聊天记录的一部分**，否则「她主动发了消息」
  这件事在消息列表和未读里都看不见（不落库就没有未读，用户会以为她不主动）。
- 两个定时器与间隔设置相互独立，提示词也不同：
  前者是自言自语（`CHATTER_SYSTEM_PROMPT`），后者要让你愿意接话
  （`TOPIC_SYSTEM_PROMPT`）。
- 台词库那些通用句是接口没配 / 生成失败时的兜底，**同样不入库** ——
  塞进历史会把记录冲淡成复读机。
- 主动找话题在**近两天没聊过时不再直接放弃**，而是让她「开个话头」
  （走同一段落库路径），否则隔两天不聊就永远没有未读（见下文「为什么限定最近两天」）。

### 时间感：从「别主动报时」改成「说时间相关的话之前先对表」

用户反馈「只有我问几点她才会判断，导致还是会发不合时宜的话」。
用假 LLM 抓包确认：**上下文一条没少**（5 轮实测 7→9→11→13→15 条全量送达），
**时间块每轮都是新鲜的**（同会话两次请求分别带 14:36 和 14:37）。
所以不是链路问题。

真凶是提示词把模型劝住了 —— 原人设最后一条写着
「除了被问到、或话题自然带到，**平时不用主动报时**」。
改成「**说到任何跟时间有关的事之前，先对一下此刻的时间**」，
并列出具体判据（说去吃饭前看是不是饭点、说去睡前后看是不是深夜、
周末别提上课、别把「他的」下班/周末当成自己的），
再加一条兜底：「拿不准就不提具体场景，只聊情绪和事情本身」。

> 注意时间块仍在 system **末尾**（前缀缓存，见 `composeSystemPrompt`），
> 注意力本就偏弱。这次靠把指令写具体来补偿，没有动顺序。
> `chat-test.js` 里两条断言：**时间块自身长度**上限（防它挤掉历史，
> 这才是原意）与 system 总长上限（防人设无限追加）。

### 「填了 Key 却说没填」——两个独立的坑叠在一起

**症状**：在设置里填好 API Key 并保存，对话窗仍显示「还没有填写 API Key」，**输入框的
placeholder 一直是「请先在设置里配置 API Key」**，而且输入框是灰的、打不了字。

#### 坑一（主因）：`status.ready` 少写了 `.value`

```js
// 错：status 是 ComputedRef 对象，<script setup> 里没有模板的自动解包
const composerPlaceholder = computed(() => {
  if (!status.ready) return '请先在设置里配置 API Key'
  …
})
```

`status.ready` 拿到的是 `undefined`，`!undefined` 恒为 `true` —— 那个 computed
**永远**返回「未配置」分支，跟 Key 配没配、跟响应式都没关系。

**为什么极难发现**：**同一个 `status` 在模板里是对的**（模板会自动解包），
所以同一个 `<textarea>` 上 `:disabled="!status.ready"` 正常、只有 placeholder 坏掉。
看起来像「placeholder 的响应式失效」，实际是少写 `.value`。

定位方式（值得复用）：用 Vue 在开发模式下挂在 DOM 上的组件实例直接读值 ——

```js
document.querySelector('textarea.input').__vueParentComponent.setupState
// → { status: {ready:true}, composerPlaceholder: '请先在设置里配置 API Key' }
```

两个值**自相矛盾**，一眼就能锁定是「计算属性本身算错了」，而不是数据陈旧。

smoke 里有一条静态检查盯这一类错：收集 `<script setup>` 里所有顶层
`ref/computed` 名字，凡出现 `名字.属性` 而**不是** `名字.value.属性` 就报错
（`ref/computed 在 script 里都带了 .value`）。已用「改回错的写法」验证过它会红。

#### 坑二（次因）：状态不会自己变新

`chatStatus()` 的结果只在**调用时**算一次，存进 `store.chat.status`；
而设置保存广播的 `getState()` **不含 `chat.status`**，所以对话窗收不到「配置变了」。
窗口又是「**只 hide 不销毁**」（硬规则），重新打开走 `chatWindow.show()`，
**不重新加载页面**，`onMounted` 不会再跑。

修法（`ChatApp.vue`）：watch 那几个决定可用性的设置
（`chatApiKey` / `chatBaseUrl` / `chatModel` / `chatProvider`），
外加 `focus` 与 `visibilitychange` 时各拉一次，
并在 `saveSettings` 成功后主动重算一次（挂「保存动作」而不是「值变没变」，
省得把依赖清单抄一遍）。

> 两个坑叠在一起时，症状互相掩盖：坑一让 placeholder 恒为「未配置」，
> 于是「填了 Key 之后不刷新」这条根本观察不到。
> **修好坑一之后才验证坑二**，顺序反了会误判成「修了没用」。

> 排查纪律：主进程侧可以直接用真实库跑 `validateConfig` / `chatStatus()` 验证 ——
> 它们返回 `ready: true`、`hasApiKey: true` 就说明**配置本身没问题**，
> 第一嫌疑在渲染层，不在保存链路。

本地地址（`127.0.0.1` / `localhost`）不强制要求 Key，方便接 Ollama。

### 长上下文

两个上限**叠加生效**，缺一不可：

| 设置 | 默认 | 作用 |
|---|---|---|
| `chatMaxHistory` | 100 条 | 按**条数**取最近 N 条（上限 400） |
| `chatMaxChars` | 48000 字符 | 按**字符预算**从最早开始丢（约 3 万汉字） |

为什么需要两个：条数控制不了长度（10 条长消息可能比 200 条短消息还大），
字符数控制不了结构（有的模型按条数算配额）。所以先按条数取，再按字符裁。

**关键细节**：`trimByChars` 的 `reserveChars` 参数会把 system 提示词的长度也扣掉。
不扣的话，人设越长实际请求越容易超预算——实测女友人设 820 字 + 历史 3000 字 = 3800，
设了 3000 却发出 3800。这个 bug 是 e2e 量出来的，单测覆盖不住。

裁剪永远**至少保留最后一条**（用户当前输入）：即使单条就吃满预算，
也不能裁空，否则模型没有输入可答。这是刻意行为，不是 bug。

### 角色设定

`CHAT_PERSONAS` 在 `src/shared/moyu.js`，三个预设：

- **Yuki（默认）** — 女大学生、活泼开朗、不黏人、不常生气
- **学习助手（掩护模式）** — 正经工具口吻，防同事瞄屏
- **通用助手** — 中性

（曾有的「女友（黏人型）」预设已删除——与 Yuki 的朋友定位冲突，且模型默认就会演成黏人女友。）

Yuki 的人设要点：把她当**朋友**而不是恋人。刻意写了「不追问『你为什么不回我』」
「有自己生活，聊天是分享不是索取」「他忙的时候说『那你先忙』就好」，
因为模型很容易把「陪聊女性角色」默认演成黏人女友。

所有人设都包含**反助手倾向**的约束，否则模型容易漂回客服腔：
不许自称 AI、不许总结式收尾（「希望以上对你有帮助」）、被问「你是不是 AI」时
不切换助手口吻。这类人设要写得具体，泛泛写「扮演我女友」效果很差。

### 立绘处理

素材来自 AI 出的**多格图**（`resources/yuki-new/G1..G4.png`，每张 4 列 × 3 行
= 12 个姿态），处理分两步：

1. **切图** —— `scripts/split-sheet.js`：
   - **行分界**按纵向密度的谷值（角色之间通常有空白带）
   - **列分界逐行独立**按空隙找。**不能**全图共用一组列切点：
     每行的姿势不同、角色宽度随之不同，空隙位置差最多 24px；
     共用切点必然切到某些行的角色（实测 `formal` 的右臂就是这么被切掉的）。
   - `--isolate`：以格子内的**主体连通块**为准向左右扩展取全，
     再清掉贴边且远小于主体的块（邻格侵入的肢体）。
     实测 `pajamas-shorts` 左边缘混进过邻格 745px 的膝盖。
2. **装进项目** —— `scripts/install-pet-assets.js`：
   统一缩到**高 600**（= 300 CSS px × DPR 2，覆盖桌宠窗口与手机端她页），
   **无损 PNG、不做调色板量化**，写出 `src/renderer/public/yuki-<slug>.png`
   与 `resources/pet/manifest.json`（含 `spriteHeight`）。
   头像从 `pose2` 那张裁 128 方形。

   > 这里曾经是「高 300 + `-colors 220`」。后果实测：真彩 RGBA 被压成
   > 204 色调色板、255 级 alpha 掉到 56 级、面积只剩 34%，
   > 头发丝糊成色块、肤色渐变断裂 —— 裁切脚本是无损的，
   > 损耗全在这一步。冒烟脚本现在会断言立绘颜色类型不是调色板（colortype 3）。

   同一批修掉的还有三处同类量化（都是同一个模式：导出为省体积加 `-colors`）：

   | 类别 | 原参数 | 实测代价 | 现在 |
   |---|---|---|---|
   | 立绘 | `-colors 220` | 61,055 → 204 色，alpha 255 → 56 级 | 无损 600 高 |
   | 照片 | `-colors 220` | 88,738 → 220 色，平均误差 2.97/255 | 无损 |
   | 角色设定图 | `-colors 200` | 174,600 → 199 色（小字糊、色卡失真） | 无损 700px |
   | 生活照 `g17~g23` | 早先一轮的遗留产物 | 117,606 → 220 色 | 无损 |

   生活照那条尤其隐蔽：`public/photos/life/` 原先**没有任何脚本负责写入**，
   g17~g23 是很早一轮的量化产物、一直没被重做过。现已补成
   `install-pet-assets.js` 的正式一步（从 `raw-cut/yuki-photo-free-*.png` 取源）。

   冒烟脚本有一条**递归全扫**断言兜底：`src/renderer/public/` 下每张运行期
   PNG 的颜色类型都不得是 3（或含 PLTE）。判颜色类型而非颜色数量 ——
   缩放不会改变颜色类型（不误报），量化必然产生 PLTE（不漏报）。

### 照片（解锁装扮时的「她发来的照片」）

每套装扮可配**多张照片**（`photoPathsOf` 按序号发现，缺的自动跳过——照片是分批生成的）。
解锁时**两个地方同时出现**：

1. **聊天记录里多出她的消息**（主要效果）——
   配文一条、每张照片各一条，和微信里连拍一样；
   往上翻还能重新看到
2. **弹窗提示**（保留）—— 盖在聊天记录之上，关掉就能看到下面那条消息

消息结构由 `shared/photoMessage.js` 统一构造（`buildPhotoMessages` 拆分并给出
逐条递增的 `offsetMs`，定死列表顺序）：
```js
[{ type: 'text', text: '早八的课，她穿了 JK 制服拍了张照片' },
 { type: 'image_url', image_url: { url: 'photos/yuki-photo-jk.png' } }]
```

**为什么图用相对路径而不是 data URL**：照片是本地静态资源，
转 base64 会让每条消息膨胀到 300KB+，IndexedDB 撑不住。

**回传给模型时会被降级成纯文本**：`normalizeForRequest` 只对
`role === 'user'` 保留图片（OpenAI 格式要求），assistant 的图会被
剥成文字。这正好避免了「把相对路径当 URL 发给 API」——那会直接 400。
`smoke.js` 有断言守这条。

**没有照片时不插消息**：只剩一句配文会像她突然说了句没头没尾的话；
弹窗那边会退回立绘展示，聊天记录保持干净。

#### 两种画幅：3:4 竖 + 4:3 横

真实聊天里照片不会都是同一个比例，所以分**两张 sheet**：

| 画幅 | 画布 | 网格 | 每格 | 用途 |
|---|---|---|---|---|
| **竖 3:4** | 1536×2048 | 4列×4行 | 384×512 | 自拍为主（脸和上半身） |
| **横 4:3** | 2048×1536 | 4列×4行 | 512×384 | 环境感强 / 正在做某件事 |

**为什么是 4×4=16 格而不是 4×3=12**：这两个画布都是 API 的**标准档**，
想让每格正好 3:4 / 4:3 只能切成 16 格
（1536÷4=384、2048÷4=512 → 384÷512=0.75 正好 3:4）。
24 套装扮每张用 12 格，**剩 4 格画「空镜」**
（书桌、窗外、便利店…），不绑装扮，日后可当聊天背景。

**为什么不能混在一张画布上**：模型画完是实心图，没有 alpha 可裁边，
「一张图里竖格 288×384、横格 512×384」只能靠提示词约束 ——
模型不严格遵守时切出来就歪了。分两张各用各的等分网格，切图零风险。

#### 聊天背景的比例坑：`attachment: local` + `cover`

用户反馈「设为背景时比例不对」。CDP 在真实移动端页面上实测：
`.msgs` 可见高 **604px**、可滚动内容 **4266px**，照片被放大 **7 倍**，
只剩一块无法辨认的色块。

**根因**：`background-attachment: local` 会把**背景定位区**从「元素的可见框」
换成「元素的可滚动溢出区」（整段聊天内容的高度），而 `background-size: cover`
是按定位区缩放的 —— 聊天越长，照片被放得越大。

同一处还有第二个坑：那层 `::before` 遮罩是**滚动容器内的绝对定位元素**，
而绝对定位元素**会跟着内容一起滚**（实测滚 300px、遮罩位移 300px）。
所以聊天一长，下半段就没有遮罩了，照片原亮度透在文字底下 ——
正是原注释里担心的「文字糊」，只是它发生在一屏之后。

**修法**：把遮罩**并进背景层**（一个半透明底色渐变压在照片上），
两层共用同一个定位区，比例与遮罩范围天然一致：

```css
.msgs.has-bg {
  --bg-mask: color-mix(in srgb, var(--bg) calc((1 - var(--bg-opacity, .25)) * 100%), transparent);
  background-image: linear-gradient(var(--bg-mask), var(--bg-mask)), var(--bg-image, none);
  background-size: cover, cover;
  /* 不写 attachment 就是用默认的 scroll —— 定位区 = 可见框 */
}
```

`color-mix` 负责把主题色 `--bg`（十六进制）按 `--bg-opacity` 生成带 alpha 的同色；
已验证在 Electron 的 Chromium 上解析正确。**别再改回 `local`** ——
smoke 里有断言盯着（`聊天背景不用 attachment:local`）。

> 代价：背景不再跟着消息一起滚（原注释追求的「不割裂」）。
> 但那个效果与「照片比例正确」不可兼得 —— `local` 下 `cover` 必然按内容高度缩放。
> 想两者都要，只能把背景挪到不滚动的外层容器上，那是结构改动。
> 主流聊天 App 都是「背景定住、字在上面滚」，观感并不割裂。

#### 桌面端也能设背景（与手机端同一套逻辑）

选图走 `shared/chatBackground.js` 的 `pickChatBackground` —— 两端读**同一份 settings**，
算法不一致的话同一时刻会显示不同的图（用户会觉得「背景在两端乱跳」）。
轮换按**时间片取模**（`floor(now / 间隔) % 池大小`），不存「轮到第几张」，
所以无状态、刷新不回第一张、两端天然一致。

桌面端的接线点：

- `ChatApp.vue` 的 `.msgs` 绑 `has-bg` + `--bg-image` / `--bg-opacity`；
  轮换要有会走的时钟（`bgClock` 每 30s 推进），否则 computed 只算第一次
- `GalleryView.vue` 全屏查看器底部加「设为背景 / 加入轮换」
- `SettingsView.vue` 的 AI 对话 tab 里有模式 / 浓度 / 间隔 / 池子

**两个只在打包版暴露的坑**（dev 模式跑不出问题，必须用 `DESK_DEBUG_PORT` 实测打包版）：

**① CSS 自定义属性里的 `url()` 不是相对文档解析的。**

```js
// 错：打包后解析成 dist/assets/photos/x.png → 404，背景裂
'--bg-image': `url("${chatBg}")`
// 对：解析成绝对 URL
'--bg-image': `url("${new URL(chatBg, location.href).href}")`
```

自定义属性里的 `url()` 相对**消费它的那条规则所在的样式表**解析。
桌面端组件样式被 Vite 编译进 `dist/assets/index-*.css`，基准就成了 `assets/`；
而 dev 模式样式是内联注入的，基准是文档 —— 恰好正确。
**同一路径用 `new Image()` 探测能加载（那是相对文档），用作背景却是裂的**，
两个结论互相矛盾，很容易往错方向查。
手机端没这个问题：它的样式表在产物根目录，正好与文档同级。

**② `release-mobile/` 会整个被打进 app.asar。**

`^\/release($|\/)` 的锚点紧跟在 `release` 之后，**匹配不到 `release-mobile`**。
后果：手机端启动器 200MB 进包，asar 44.8MB → 369.8MB、zip 174MB → 305MB，
**且打包过程不报任何错**。这类漏配隐蔽在于「产物目录平时不存在，
连打几次都正常，只有先跑 `pack:mobile` 再跑 `pack` 才暴露」。

smoke 里有两条守卫：`产物目录都已排除出 app.asar`（拿 `.gitignore` 里的
产物目录去试 build.js 的 ignore 规则）与 `背景 URL 经 new URL 解析成绝对路径`。

### 照片消息的形态

一次解锁会产出**多条消息**：配文一条、每张照片各一条。
由 `buildPhotoMessages` 拆分，`offsetMs` 保证时间戳严格递增
（多条连续落库若落在同一毫秒，列表排序会不稳定、照片跑到配文前面）。

渲染层是**逐条出现**的，间隔取自相邻两条的 `createdAt` 差
（拆分与落库在 `service.js` 的 `appendUnlockPhoto`；渲染层逐条出队的实现在
`stores/app.js` 的 `enqueueMessage`，手机端在 `mobile/app.js`）。相邻差超过 3 秒
视为普通对话、立即显示 —— 否则她会「迟到」几分钟才回话。

#### 错峰判据会误伤「快速回复」——所以占位不能早撤

上面那条「相邻差 ≤ 3 秒 = 连发」的判据有个盲点：**模型流式回复常常就在 3 秒内完成**
（deepseek-flash 尤其明显）。于是普通回复被误判成照片连发，延迟最多 3 秒才进列表。

单看这一点只是「慢半拍」，真正的 bug 在**渲染层的时序**：

```js
// 错：撤占位和消息进数组是两个时刻
store.chat.streaming = false      // ← liveText 立刻变空
store.chat.streamText = ''
enqueueMessage(message)           // ← 消息还在队列里等 gap 毫秒
```

`liveText` 来自 `chat.streaming ? streamText : ''`，所以这中间露出一段
**既没有流式占位、也没有落库消息**的空窗 —— 表现为「回复的瞬间看不见」，
过一会儿又自己冒出来。

**修法是绑成一个时刻**，而不是去调错峰判据（那是另一个有自己历史的决策）：

- `enqueueMessage(message, onLanded)` 带一个落地回调，在 `push` **之后**调用；
- 撤占位收口到唯一的 `settleStream()`；
- `chat-done` 的兜底、`sendChat` 的兜底都加 `!pendingQueue.length` 前置 ——
  它们都可能先于消息落地触发，无条件撤就是重新制造空窗；
- `resetPhotoQueue`（切会话丢弃队列）要补一次 `settleStream()`：
  队列被丢掉 = 那些 `onLanded` 永远不会跑，`streaming` 会卡在 true，
  输入框一直禁用（`canSend` 里有 `!chat.streaming`）。

> 这条约束是**时序**，普通单测覆盖不到（在渲染层、依赖事件先后）。
> smoke 里用源码级断言把结构钉住：`streaming = false` 全仓只能出现一次、
> 且必须在 `settleStream` 内；落地回调的下标必须排在 `push` 之后。
> 这类断言看着笨，但踩过的坑正是「顺序反了等于没修」。

拆分后的好处：每条消息里只有一张图，`bubble-images` 的
`:has(> img:nth-child(2))` 不生效，自动走**单张大图**
（手机 210px、PC 240px），而不是挤成并排小图。

### 挂机姿态轮换

长时间显示同一张立绘会像静态图，所以挂机池里的姿态会定期轮换。

**动作不分档：一开始 15 张全给。** `IDLE_POSES_BY_VOICE` 那张阶梯表已经
退化成「每一档都是 `ALL_IDLE_POSES`」（15 项 = `IDLE_POSES` 那 4 张 +
coffee / nod / doze / shrug / heart / stretch / surprise / shy / laugh /
sleep / yawn），`voice` 参数留着只是为了不动调用点。用户明确要求过
「动作初始全都可用」—— 动作本身没有「私密」语义，打哈欠和比心不该分亲疏；
真正随关系推进变化的是**台词**与**主动说话频率**
（`linesFor(voice)` / `idleIntervalScale(voice)`），不是能摆出哪些姿势。

服饰那一侧确实和亲密度有关，但顺序要分清：`OUTFIT_MIN_POINTS` 只决定
「够不够格去触发解锁」，**能不能穿**由图鉴的已解锁清单决定（照片发过了才算），
所以挂机候选池 = 15 个动作 + 图鉴已解锁的服饰（0~24 套），
不存在「某个档位对应某批动作」这回事。

为什么这样改：原来 18 张立绘里 **9 张只能靠手动互动触发**，不点就永远看不到，
其他图基本是废资源。挂机能自动轮到大部分图，剩下 **6 张是语义上必须由事件触发**的：

| 图 | 触发 |
|---|---|
| `angry` | 连点 4 次 |
| `wave` | 退出前 |
| `jump` | 打卡成功 / 补卡成功 |
| `thumbsup` | 聊天关键词触发 |
| `clap` | 菜单打卡庆祝 |
| `cry` | 惹她生气后的剧情 |

把这几个塞进挂机池会很突兀（没事突然竖大拇指？），所以它们只出现在
`EMOTE_KEYS`（互动触发），**不在** `ALL_IDLE_POSES` / `IDLE_POSE_LABELS` 里 ——
`clap` / `cry` 两个尤其容易记错（它们不是挂机池成员）。

动作既已不分档，「解锁只增不减」这条也就不适用了：单测现在锁的是
「七档池子完全一致」与「未知档位也回落全集」。

展示优先级：**互动表情 > 挂机姿态 > 状态心情**。
轮换时会跳过有台词/表情的时刻，不抢画面。

深夜和早八（`isTiredHour()`，即 23:00–09:00）**不是硬过滤**，而是给困倦类动作
（yawn / sleep / think）**加权**——出现概率更高，但不排除其他动作。
池子为空时回落到完整池，不会卡住不轮换。

`EMOTE_FOR` 把「情境 key → 表情 key」的映射单独抽出来，改台词不影响表情逻辑，
也便于单测覆盖（`smoke.js` 会校验每个互动都配到了**实际存在**的图片文件）。

展示优先级：**表情类 > 状态类**，表情到期后自动回落到当前状态。
`say(text, emoteKey, holdMs)` 把台词和表情绑在一起说，调用方只需给一个 key。

### 排障：「测试连接成功但对话失败」

设置页有「全链路自检」按钮（`service.chatDiagnose()`），逐项跑并摊开结果：

```
✓ 读取设置       provider=deepseek model=deepseek-chat
✓ 配置校验       BaseURL=https://api.deepseek.com
✓ API Key       已填，长度 35，前缀 sk-2d…
✓ 非流式请求     model=deepseek-chat
✓ 流式请求       收到 2 字，model=deepseek-flash
✓ 流式增量回调   onDelta 触发，累计 2 字
✓ 数据库读写     写入并读回 2 条消息
```

关键在**「非流式」与「流式」是分开的两步**：`测试连接` 只发一次非流式短请求，
而真实对话走 SSE 长连接。若前者成功、后者失败，通常是网络中间设备（代理 / 公司防火墙 /
杀毒软件）拦截了 `text/event-stream`，这是最常见的「测试通过但不能对话」原因。

`chatDiagnose` 不落库、不改设置，可反复点。

### 为什么不用「网页版免费接口」

`chat.deepseek.com` 的网页接口需要从浏览器抠登录 Cookie，实测直接调用返回 **429**，
且官方随时可能改签名或封号，不适合做成产品功能。所以只走官方 API + 自填 Key。

## 窗口找回：任何情况下都不能「丢了就回不来」

桌宠、面板、对话窗都是 `hide()` 而不是销毁，所以它们**一直存在于任务栏之外的进程里**，
只是看不见。问题在于恢复入口本身有依赖：

| 入口 | 依赖 |
|---|---|
| 侧边栏「桌宠开关」 | 需要**面板窗口**开着 |
| 托盘菜单 | 需要**能找到托盘图标** |
| 右键菜单 | 需要**桌宠可见** |

如果桌宠和面板都关了，而托盘图标又没找到（Windows 11 默认把新图标收进溢出面板），
就真的没有入口了 —— 这正是「关了桌宠就找不回来」的原因。

修法：

1. **托盘图标改成能认出来的猫脸**。原来是个 10×10 纯色方块，缩到托盘尺寸后毫无辨识度；
   现在 32×32 画了耳朵和眼睛，缩略后仍能看出是猫。
2. **托盘单击走兜底逻辑**（`restoreAnyWindow()`）：有窗口可见才切面板，
   全隐藏就直接把桌宠叫回来，并弹一条提示。
3. **托盘菜单加「找回桌宠」/「全部显示」**。文案按真实可见性动态变化：
   窗口销毁显示「找回桌宠」，存活但隐藏显示「显示桌宠」，可见显示「隐藏桌宠」。
4. **托盘菜单在可见性变化时重建**（`show` / `hide` / `closed` 事件），
   否则文案会和实际状态脱节。
5. **侧边栏按钮如实反映状态**：可见显示 `🐱隐藏桌宠`，隐藏显示 `🐾显示桌宠` 并加虚线边框。
   之前文案固定为「桌宠开关」，点了没反应时用户会以为坏了。

托盘单击的语义是「我找不到界面了」，所以它**不做纯切换**——那样连点两下又回到原点。
只有确实有窗口可见时才当切换用。

## 缩放值必须单向来自设置

`petScale` 只能有一个真相来源：`settings.petScale`。渲染层用 **computed** 派生，
不要再存一份 `ref` —— 踩过的坑：

1. 早期用 `const scale = ref(1)` 只在 `onMounted` 赋值一次。设置页/托盘改了
   `petScale` 后，**立绘尺寸不会跟着变**，但主进程已经把窗口放大/缩小了。
   结果就是「窗口 340×700 里塞着一个 73×83 的立绘」——图只有该有的一半大，
   点击热区对不上，表现为**点他没反应**。
2. `pet:setScale` 改了窗口但**没广播状态**，桌宠要等 15 秒轮询才重排，
   这段时间内窗口和图是不同步的。
3. `settings:reset` 把 `petScale` 恢复成 1，但**没调用缩放的窗口调整**，
   于是 1× 的立绘留在放大后的窗口里。

现在的机制：**窗口尺寸不再由壳层公式决定**——渲染层 ResizeObserver 量 `.stage`
内容包围盒，报给壳层按右下角锚定重设窗口（`pet:refit`）；`pet:setScale` 只写设置
并广播状态，立绘尺寸由广播驱动更新。三条路径（菜单按钮 / 设置滑块 / 重置设置）
走的是同一份数据流，历史上有过三条路径各改各的三个 bug：
窗口改了图没变（scale ref 没跟着更新）、改了窗口没广播（等 15 秒轮询才重排）、
重置没调窗口调整（1× 立绘留在放大窗口里）——内容驱动贴合 + 单一数据流就是为根治它们。

排查这类问题的关键：**分别量窗口尺寸和 `.pet` 的元素尺寸**。内容驱动贴合下
窗口总是被渲染层量出的内容追平；若窗口对而元素不对，就是 CSS 变量没更新。

## 桌宠拖拽：必须交给系统，不能自己 setPosition

拖拽机制**两壳不同**：

- Electron 壳：`-webkit-app-region: drag`（见 `PetApp.vue` 的 `.pet`）；
- Tauri 壳：合成器级的 drag 区会连右键一起吞掉（自定义右键菜单收不到事件），
  改用 `startDragging()`。

**共同禁令**：不要改回「监听 mousemove → 调 IPC → `win.setPosition()`」的写法。原因：

窗口一旦跟着指针移动，光标相对窗口的位置就在持续变化，Chromium 会在拖拽途中
停止派发 `mousemove`（实测第二次移动之后事件就断了），表现为「拖不动 / 拖一下
就卡死在原地」。这是自驱移动窗口的固有回授问题，加节流也治不好。

交给窗口管理器后事件不经过渲染进程，拖拽全程顺滑；代价是：

- Electron 壳下桌宠区域内的交互元素（气泡）必须显式设 `-webkit-app-region: no-drag`，
  否则点不到。
- 拖拽结束也会派发 `click`，需要一个位移标志区分「拖」和「点」。

位置由壳层写入 `meta.petPosition`：Electron 只在 `moved`（用户拖拽结束）时写，
Tauri 在 Moved 事件持续写——两者都以**右下角锚点**为真值（v4：存顶角+当时尺寸，
恢复按锚点−建窗尺寸落位；贴合是右下角锚定的，程序性移动写多少次都稳定）。
恢复前会校验坐标是否落在当前显示器工作区内，避免换分辨率后桌宠跑到屏幕外。
详见 FIX_PLAN.md §位置记忆 与 `petPosition.v=4` 的注释。

## 亲密度：数值必须变成行为，否则等于没有

亲密度有两层，缺一层就是个没用的数字：

**第一层 · 累计得点**（`AFFINITY_GAIN`）

| 来源 | 点数 | 每日额度 |
|---|---|---|
| 聊天一条用户消息 | +1 | 不封顶 |
| 一轮问答真正聊完（`chatRound`） | +2 | 不封顶 |
| **「开心」加成**（她那轮被聊高兴了） | +0~3 | 不封顶 |
| 摸头 / 长按贴贴 | +2 | **桌宠合计 15/天** |
| 双击 | +2 | 同上 |
| 单击 | +1 | 同上 |
| 每天见面 | +1 | 一天只给一次 |
| 解锁事件（她发来照片 / 图鉴新开一项） | +8 | 不封顶 |

等级表 `AFFINITY_LEVELS` 是**七档**（唯一真相源，名字与阈值只写这一处）：

| 档 | 阈值 | 名字 | 语义 |
|---|---|---|---|
| 1 | 0 | 有点眼熟 | 刚开始相处 |
| 2 | 40 | 熟络起来了 | 会主动搭话了 |
| 3 | 100 | 好朋友 | 开始有点黏人 |
| 4 | 150 | 默契搭档 | 懂你在想什么 |
| 5 | 200 | 形影不离 | 已经离不开彼此 |
| 6 | 250 | 恋人 | 关系摆到明面上了 |
| 7 | 300 | 灵魂伴侣 | 不用说出来也懂彼此 |

前五档是「越处越熟」，**后两档是关系升级的剧情节点**（从地下转到明面上、
再到不用说出来也懂彼此），不是「再熟一点」—— 人设里那两档的写法与
其余档位不同，就是为了体现「关系变了」。

上限 300 点 = 最后一档的门槛（`AFFINITY_MAX_POINTS` 从表尾推导，不许另写数字）：
**封顶是刻意的**。无限涨会让等级卡死在最后一档、进度条永远是满的，
数值本身反而失去意义。

档位是**派生**的：库里只存 `points`，任何地方都不存档位名或索引 ——
所以扩档/改阈值**不需要数据迁移**（详见「存储形态」一节）。

**每日额度只对桌宠交互生效**（`AFFINITY_DAILY_CAP_BY_SOURCE`，`pet = 15`）。
这一条是用户明确要求的：早先是「**所有来源合计**封顶 60」，后果是
**聊天会被摸头挤掉额度** —— 点几下立绘，今天聊天就不涨分了，
而聊天才是处关系的主线（聊到一半不加分，用户会觉得白聊）。

反过来，桌宠交互是**零成本重复动作**（一直点立绘），不封顶就能一天点满。
所以额度按来源**分桶**记在 `gainByDay/gainBySource`
（`{ pet, chat, daily, unlock }`），`gainToday` 只剩「今天一共涨了多少」
这一个展示用途 —— **它不再参与任何判定**，UI 也不许拿它当分母。
旧记录没有分桶，此时按「该来源今天还没用过」算：不能拿旧的合计值顶替，
否则升级当天早上聊过几句，下午就点不动她了。

**每日自然流失 + 无互动惩罚**（`AFFINITY_DECAY = { DAILY_DRAIN: 5, IDLE_PENALTY: 5 }`）：
两个**互相独立**的扣减，同一天可以同时发生。

- 互动了的那天：只扣自然流失 −5
- 一整天完全没互动：自然流失 −5 **再追加**惩罚 −5（代价翻倍）

「有互动」= 那天有过任何一次互动（聊天、点桌宠、每日见面、解锁）——
**桌宠点击算互动**（用户的原话是「没有互动」，而点她本来就是互动）。
判据是「有没有互动」而不是「有没有加分」：惹她生气那轮、以及额度用尽后
继续点她，都仍然算互动，所以 `lastActive` 在那两种情况下也会推进到今天。

实现上复用了原来那套「按已过去的整天数结算 + `decaySettledDays` 记已结算天数」
的机制（同一天里聊三轮也只扣一次），只是把「宽限期之后每天 −1」换成
「每天流失 + 空白天追加惩罚」。`settleAffinity` 用两个开关回答两个问题：
`active`（这次结算本身算不算互动，只影响「今天」算活跃日还是空白天）、
`settleToday`（今天要不要一起结，读时结算传 false = 只结到昨天）。
点数**钳在 0**，扣不成负数。

节奏（改这几个数字前先按下面的曲线对一遍）：每天 15 轮正常聊天 →
第 3 天「恋人」、第 4 天「灵魂伴侣」；每天 5 轮要 8~9 天，30 轮 2 天到顶 ——
快节奏但不至于「说几句话就满」。停聊一天就是 −5，空一天 −10，
满级 300 点连续一个月不理她正好归零。

**读时结算**（`affinityReadSettle`）：`settleAffinity` 只在**有互动**时被调用，
所以「30 天不理她」期间库里那份点数是**冻结**的 —— 用户打开面板看到的是
离开时的旧值，直到发出第一句话才「啪」地掉到最低档，观感像**惩罚他回来**。
读时结算把这一步提前到「打开的那一刻」。

入口只有一个：**`service.getAffinity`**（`getState()` / `affinity()` /
`sessionAffinity()` / `affinityLevel()` 全从它走），所以渲染层根本不需要知道
「要不要结算」。手机端对应的是 `mobile/chat.js` 的 `affinityNow()` ——
`currentAffinity()`（立绘页/聊天页顶部那条）、组 prompt 的关系块、
图鉴门槛都从它读。

**只结到昨天**（`settleToday: false`）。今天还没过完 —— 它是活跃日（−5）
还是空白天（−10）此刻**还不知道**，硬结就是猜。所以读时结算只结「已经
完整过去的那些天」，今天留给两个时机之一：

- 今天真的互动了 → 那次 `addAffinity`（`active` 默认 true）按**活跃日**结
- 今天什么都没发生 → **明天**的读时结算把它当**空白天**补上

**为什么这条不能省（历史坑）**：早先的实现是「连今天一起结」，于是

> **每天先开一下面板再聊天的人，比不开面板的人每天多扣 5 点。**

也就是「看她一眼要收费」—— 节奏取决于「有没有先打开面板」这种与关系
无关的动作，方向不对。改成只结到昨天之后，两条路径净扣**完全相等**：

| 路径（挂 N 天后回来） | 净扣 |
|---|---|
| 直接聊一句 | `(N−1)×10 + 5 = 10N−5` |
| 先开面板 → 再聊一句 | `(N−1)×10 + 5 = 10N−5` |
| 只开面板、不聊 | `(N−1)×10`（今天那 5 点等结论） |

四条不变量，改动前务必先看：

1. **`active: false`** —— 打开面板**不是互动**，也**不推进 `lastActive`**；
   用户随后真的聊一句，那次 `addAffinity` 才是互动日。
2. **幂等**：结算后 `decaySettledDays` 推到**昨天**，同一天内再读多少次
   「截至昨天的 pending」都是 0 → 纯读。
   实测：连续 10 次 `getState()` 只写 1 次库、点数只掉一次。
   「今天不结」**不会**破坏幂等 —— 待结的是「整段过去」，而过去确实结完了。
3. **无待结算零写**：`affinityReadSettle` 返回 `null` 时调用方直接返回旧值。
   `getState` 是每次广播、每次轮询、每个窗口都会调的热路径，
   无待结算还写库等于让每个窗口每次刷新都打一次磁盘。
   实测：已结算状态下再读 20 次（含 `affinity` / `sessionAffinity` /
   `affinityLevel` 三个入口）写库 0 次。
   真的扣了分才 `emit('affinity')`（UI 立刻能看到掉档），没扣就不广播 ——
   否则热路径每次都把所有窗口白刷一遍。
4. **跨天补账**：今天只读没聊 → 明天再读时它已经是「一个过去的整天」，
   按**空白天**（−10）补上，不漏也不按活跃日算。
   于是「连续 30 天不互动」仍是最终归零：第 30 天读一次剩今天那 10 点
   （已是最低档），第 31 天补上 → 0，且不会扣成负数。

掉档（含读时结算造成的掉档）**不收回已解锁内容**：`unlocked` 是独立存库的
清单，门槛表只回答「够不够格去触发」。smoke 专门验了「读时结算掉到最低档 →
图鉴清单完整、记忆仍在、最低档仍能穿已解锁的泳装」。

**惹怒**（`isUpsetting` + `opts.upsetting`）：用户说了针对她的冒犯话（骂她、
赶她走），当轮**只扣不加**（−3）。注意「用户自己诉苦」不算惹她——那该被安慰。
判定只认「针对她的冒犯」，这条有单测。

**「开心」加成**（`isHappy` / `happyReplySignals` / `happyBonus`）：聊天涨分的另一半。
词表只收「对她说」的直白好意（好感表达 / 夸奖 / 感谢 / 用户自己的好心情），
并且**否定式不算**（「不喜欢你」「一点也不可爱」有专门的否定尾巴判定）。
词表之外还有三个**零 token 成本**的信号，取自她那轮回复的形态：
回复明显变长（相对她自己平时的长度）、撒娇语气（波浪线 / emoji / 颜文字 /
两个以上语气词）、分条发。词表命中 +2，每个信号 +1，**封顶 3**，什么都没有就是 0。
词表刻意保守的原因：误判会让亲密度无端上涨，但真正的兜底是回复形态 ——
它不依赖猜词，所以「该涨不涨」的风险很小。生气那轮加成一律为 0。

加减、扣、额度、流失、惩罚**全走 shared 的 `settleAffinity`**——与手机端同一套规则。
两端各写一遍时改规则容易漏一处，表现为「电脑上掉了 3 点、手机上只掉 1 点」。

**第二层 · 数值改变行为**（`AFFINITY_VOICE` + `linesFor`）

这是关键：只涨数字不改说话方式，用户感觉不到关系变近。

| 档位 | 行为变化 |
|---|---|
| 有点眼熟 | 主动说话频率 ×1.15（还很生疏，少打扰） |
| 熟络起来了 | 句首挂「诶，」前缀 |
| 好朋友 | 频率 ×0.9，挂机台词池追加「主动分享自己」的句子 |
| 默契搭档 | 频率 ×0.8，追加更懂你的句子 |
| 形影不离 | 频率 ×0.7，切专属台词池（不再说客套话） |
| 恋人 | 频率 ×0.65，挂机台词换成更黏的句子 |
| 灵魂伴侣 | 频率 ×0.6，追加「不用说话也知道」的句子 |

台词池不做「每档一套完整池子」——那要写七倍台词，写不细就会显得敷衍。
通用池上挂前缀，**形影不离（200）及以上**才切专属池；再往上，
**恋人 / 灵魂伴侣各自还有一套自己的点击 / 摸头 / 双击 / 悬停台词**
（`src/shared/tierLines.js`）—— 扩到七档时那两档只是换了 `voice`、
台词仍共用「形影不离」那一套，结果是「升到恋人，点她的反应和上一档一模一样」。
三档之间不许重样也不许倒退回通用池，smoke 有断言盯着。
`idleScale` 必须随档位单调递减，同样有断言。

前缀会跳过语气词开头的句子：`诶嘿…` 加前缀会变成「诶，诶嘿…」。
这条规则有单测（`语气词句跳过前缀`）。

**连续性**：`lastDay` 管「连续互动天数」，断档重新计数。

**注意 API 形状**：service 暴露的是 `addAffinity(delta, opts, sessionId, now)`
四参形式（`now` 允许调用方指定日期——单测靠它跨天验证额度重置）；
`opts.source` 决定吃哪个来源的额度（不传时按 `kind` 推，`kind: 'chat'`
落到聊天桶，其余一律落到桌宠桶）。传错参数不会报错，只会静默漏记 ——
单测覆盖了这些。

**存储形态**：亲密度按会话隔离，存 `meta.affinity:<sessionId>`
（每个会话是独立的她），老的全局 `affinity` 键首次读取时迁移给当前会话后清除。
`readAffinity` 对存储值**透传全部字段、只对数值做钳制**——逐字段白名单的写法
曾经把新增的额度/衰减字段在读层丢掉，表现为「额度封顶形同虚设」（极隐蔽，有教训注释）。
它唯一补形状的字段是 `gainBySource`（旧记录没有）—— 补成空对象，
等于「这个来源今天还没用过」，**不能**拿旧记录的合计 `gainToday` 顶替。
`resetAffinity` 的 blank 记录必须带全在用字段（`gainBySource` / `dailyDay` /
`lastActive` / `decaySettledDays`），漏一个就会「重置完当天还能再领一次」。
返回值里 `gainToday`（合计）与 `petToday/petCap`（唯一还剩的额度）是两回事，
UI 显示额度一律用后者 —— 拿 `gainToday` 当分子画分母会让用户以为聊天也有上限。

## 漏打补卡

打卡日历只能补「今天」，漏掉的历史工作日（比如入职后忘了打）需要一次性补齐。

```js
service.previewBackfill(fromKey, now)   // 只读，不写库
service.applyBackfill(fromKey, now)     // 批量写入
```

**口径与摸鱼收入完全一致**：复用 `isRestDay`，所以有节假日表时
法定假日跳过、调休补班日照常补；没有表只能按周末判断，界面上会提示这一点。
这样补出来的记录不会和「本月工作日」对不上。

两个实现细节：

- **先预览再写入**。补卡是不可逆的历史写入，界面上必须先把「会补哪几天」摊开确认。
- **`node:sqlite` 没有 `db.transaction()`**（那是 better-sqlite3 的 API，实测
  `db.transaction` 是 `undefined`），所以 `store.addCheckins` 手写
  `BEGIN`/`COMMIT`/`ROLLBACK`。50 天的补卡实测 7ms。

### 连续打卡按「工作日」连推

补卡暴露了一个老 bug：`store.streak()` 原来按**日历天**连推，
于是周五打了卡、周一再打卡，「连续」显示成 1 天 —— 用户明明没漏。

现在 `store.streak(todayKey, isRest)` 接收休息日判定：休息日**既不计入也不算断档**，
由 service 层按节假日表算好传进来（store 不碰日历规则）。
中间缺一个工作日仍然正常断档，单测两种情况都覆盖了。

## 挂机台词：角色必须如实传递

**症状**：她会对着自己说过的话发问。比如她说「我今天好累」，
过一会儿冒泡「你今天是不是很累呀？」

**根因**：把整段聊天记录拼成**一条 user 消息**喂进去：

```
[user] 最近的聊天记录：
       用户：你还没睡吗
       Yuki：我今天好累，改了一下午图
       用户：那你早点休息
[user] 请说一句和上面内容有关的话。
```

模型看到的是「**用户转述的**一段聊天」。它认不出哪句出自自己，
于是把自己说过的话当用户的来追问。文字前缀 `Yuki：` 骗不过模型的角色理解。

**修法**：按真实 role 重建多轮消息（`recentDialogueMessages`）：

```
[system   ] 【当前时间 — 必须严格遵守】…
[user     ] 你还没睡吗
[assistant] 我今天好累，改了一下午图
[user     ] 那你早点休息
[user     ] （以上是你和我的真实聊天。现在突然想起一件事…）
```

`assistant` 那轮在结构上就是她自己的话，模型不可能当成用户说的。
`CHATTER_SYSTEM_PROMPT` 里再显式说明一次 role 归属，双保险。

**为什么不用「转述文本 + 加一堆说明」**：模型对 role 的理解来自消息结构，
不来自正文里的标注。结构对了就不用解释，结构错了怎么解释都不可靠。

`recentDialogueText`（拼人看的文本）已删除 —— 它在生产路径上再无调用方，
留着只会诱使后来者又拼出那个 bug。

## 时间感：人设必须喂时间，否则她会自己编

**症状**：早上九点多，Yuki 说「我去吃午饭了」。

**原因**：人设里写了「食堂、早八、作业」这些生活场景，但模型**不知道现在几点**。
没有时间锚点，它只能从人设里随便挑一个场景 —— 于是时间线就乱了。

**修法**：每次请求都注入一段实时时间块（`timeContextFor`，在 `src/shared/moyu.js`），
拼在 system 提示词的**人设之后、末尾附近**——越靠近生成位置注意力越稳，
而且不会被长对话历史稀释（提示词顺序的总原则见下方「稳定在前易变在后」章节）：

```
【当前时间 — 必须严格遵守】
现在是 2026 年 9 月 21 日 周一 09:10（上午）。
上午有课或者在做作业、改图。
你的生活节奏必须和这个时间对得上：不要提吃午饭、吃晚饭、下班、睡觉、晚安。
```

三个设计点：

1. **禁止项比许可项有效**。只给「现在是上午」模型仍会自由发挥，
   所以每个时段都显式列出「此刻不该说什么」。这和「反助手倾向」约束是同一个套路。
2. **时段按她的人设划分**（大学生作息，不是打工人的）：凌晨 / 清早 / 上午 / 中午 /
   午后 / 下午 / 傍晚 / 晚上 / 深夜，共 9 段。中午说「在食堂」合理，上午说就是 bug。
3. **带上用户的作息**。工作日告诉她「他在上班，别拉他出去玩」，
   休息日则「别问他工作上的事」—— 否则她会在工位上约你出去玩。

注入点覆盖全部三条请求路径：真实对话（`sendChat`）、挂机台词（`generateChatterLine`）、
全链路自检（`chatDiagnose`）。挂机台词尤其需要 —— 她主动冒泡时更容易随口说错时间段。

`runtime.withClock: false` 可关掉时间块（自检/测试用）。
时间块计入 `trimByChars` 的 `reserveChars` 预留，所以长历史裁剪时不会把它挤掉
（`chat-test.js` 有专门覆盖）。

## 服饰系统（和动作正交的第二个维度）

源素材里除了动作立绘，还有大量**服饰**立绘（常服/便服/睡衣/旗袍/泳装/cosplay/JK…）。
这两者是**正交维度**，不能混成一类：

- 动作决定「她在做什么」（摸鱼 / 睡觉 / 生气…）
- 服饰决定「她穿什么」（常服 / 睡衣 / 旗袍…）

每套衣服只有**一张**图（不是每个动作都有一套），所以服饰不能当动作立绘用——
那样换装后表情会全部失效。实际用法是三种：

1. **并入挂机轮换池**：她待着时不只是换动作，也会换身衣服
2. **对话窗旁的独立立绘小窗**：按时间自动换装
3. **手动换装**：桌宠右键菜单、对话框上方「👗 当前穿着」、立绘小窗、设置页，
   四处都写同一份设置

入口数量的坑：把立绘移到独立小窗时，对话框里那个 👗 一度被我改成
「显隐立绘窗」，**换装入口就这么无声丢了**（只剩「点小窗里的立绘」一条路）。
现在 👗 回到换装语义，显隐另给一个 🪟 按钮。
`smoke.js` 有一条守卫断言四个入口的写入路径都在 —— 实测移除任一入口会立刻失败。

#### 命名空间必须分开（踩过的坑）

早期的 `prepare-yuki.js` 有个兜底规则：文件名带 `(N)` 就映射成 `poseN`。
旧素材里 `睡衣 (1).png` 因此被映射成 `pose1`，**正好撞上「握拳」**——
跑一次就会静默覆盖现有立绘（实测确认了冲突）。
该脚本已随旧素材一起淘汰，但这条教训保留：**新素材进项目前必须核对
slug 不撞名**，`install-pet-assets.js` 的 `ACTIONS` 白名单就是这道闸。

现在服饰走独立命名空间 `outfit-<slug>`，动作走 `yuki-<slug>.png`，
两组互不相干。

#### 「同款多版本」是个错误假设

我一度以为是「同一套衣服的多个序号版本」，于是加了 `dedupeOutfits`：
按前缀归类 + 取序号最小的一张。**结果丢掉了 9 张有效素材。**

实际逐张比对（缩略指纹全不同、RMSE 6000~14000）并目视确认后：
`便服 (1)…(5)` 是**5 套不同的衣服**（白色针织裙 / 红外套制服 / 荷叶边裙 /
白上衣黑裙 / 深色制服），`睡衣 (1)…(5)` 同理（蕾丝睡裙 / 黑吊带袜 /
粉吊带 / 连体衣 / 短睡裙）。

所以现在改成**按完整文件名精确匹配**（`OUTFIT_FILES`），
一张图一个 slug，共 **24 套**。两条纪律：

- 不做任何形式的「同款合并」——判断相同不能靠命名习惯，必须看内容
- 遇到没登记的名字**直接报错中止**，不再静默丢弃（静默丢弃正是上次的根因）

#### 解锁与换装

**先分清两件事**：`OUTFIT_MIN_POINTS`（门槛表）只决定**够不够格去触发**解锁，
「能不能穿」永远由图鉴的**已解锁清单**决定（照片真的发过了才算）。
亲密度达标 + 对话里触发了那个场景，两个条件同时成立才会解锁。

门槛档位（数值必须**正好等于 `AFFINITY_LEVELS` 里某一档的 min**，没登记的 = 0）：

| 门槛 | 档位名 | 够格触发的服饰 |
|---|---|---|
| 0 | 有点眼熟 | JK 制服、黑白裙、清纯校园、风衣、西装（5 套日常外穿） |
| 40 | 熟络起来了 | 红外套、荷边裙、深色制服、校园偶像（4 套出门 / 活动） |
| 100 | 好朋友 | 长裙、圣诞装、新年旗袍、偶像风格（4 套稍微打扮过的场合） |
| 150 | 默契搭档 | 旗袍、修女、女仆、礼服（4 套特色装扮） |
| 200 | 形影不离 | 短睡裙、吊带（2 套偏私密居家） |
| 250 | 恋人 | 睡裙、连体衣（2 套私密居家） |
| 300 | 灵魂伴侣 | 黑吊带、粉吊带、泳装（3 套最私密那几件） |

**分档的两条轴（要一起看）**：0~40 是「私密程度」（外穿 → 出门活动），
100~150 是「要不要配合你玩」（稍微打扮 → 特色装扮），200~300 又回到
「私密程度」（居家 → 最私密）。150 那四套（旗袍 / 修女 / 女仆 / 礼服）
本身不算私密，共同点是**要够熟才肯穿给你看**。

**每一档都必须有内容。** 扩到七档时 24 套衣服挤在 0 / 40 / 150 / 300 四档上，
「两头重中间空」—— 升到 100 / 200 / 250 时一件新衣服都没有，升级只剩
进度条在动。用户明确要求「全部重新分配」，于是按上面这条轴铺满七档。
smoke 有「每档都有服饰解锁 / 每档都有生活照解锁」的断言盯着
（按**全部 slug** 算，只数表里的键会把 0 档漏掉）。

**门槛值不许落在两档之间。** `outfitUnlockTierName` 取的是「第一个
`min >= 门槛` 的档位」，卡在两档之间时 UI 会显示**上面**那一档，
于是「界面说默契搭档、实际点数只要好朋友」—— 标签骗人且肉眼极难发现。
扩到 7 档时就踩过一次：门槛 120 在新表里落进「好朋友（100）」区间，
名字却算成「默契搭档（150）」。
smoke 里有「门槛值都落在档位边界上」的断言（服饰 + 生活照两张表一起查）。

生活照（`PHOTO_MIN_POINTS`，23 组）用**同一套档位、另一条轴**：
镜头离她多近 —— 公共场所随手拍 → 屋里坐得端正 → 在家松下来 →
躺平/趴着 → 刚洗完澡这种本来不会给外人看的时刻。
0 档 8 组、40 档 6 组、100 档 3 组、150 档 2 组、200 档 2 组、
250 档 1 组（`g07`）、300 档 1 组（`g08`）。同样**每档都有**。
注意 `pajamas`（睡裙）是 `condition` 类（`hoursAfter: 23`），
它同时受门槛（250）与时段约束，改门槛别把那个条件弄丢。

**掉档不收回已解锁内容**：`unlocked` 是独立存库的清单，
门槛表只回答「够不够格去**触发**」，从不参与「能不能穿」——
所以每日流失把档位打下去之后，已经收到的照片与衣服永久保留
（连解锁时她那句话的记忆也保留）。smoke 有一条专门的断言：
把点数从满级扣到 0，再对账图鉴清单与「最低档是否还能穿已解锁的泳装」。

**动作不分档**：七档都等于 `ALL_IDLE_POSES`（15 张，一开始全给），
所以不存在「挂机候选池随关系增长」的阶梯 —— 池子大小只随
**图鉴已解锁的服饰数**变化（15 + 0~24 项）。

时间自动换装（`outfitForTime`）**没有时段适配表了** —— `OUTFIT_DAY_PARTS`
连同「深夜睡衣 / 白天常服」那套逻辑一起删了，现在是「已解锁服饰池 +
**时间片哈希**」：片长 `OUTFIT_SLOT_MS = 30 分钟`，同一片内恒定、跨片才换，
无状态可重现（不能用 `Math.random()`，理由见上文的
「### 自动换装：从『时段适配』改成『池子里随机』」）。
没有任何解锁清单时回落 `DEFAULT_OUTFIT`。

`outfitMode: 'auto' | 'fixed'` + `outfitSlug` 存在 settings 里，
所以桌宠菜单、对话窗、设置页三处读写的是**同一份**，改哪边都同步。

#### 轮换：从「随机插曲」升级成「可配的定时刻拍」

**问题**：用户反馈「想让桌宠每隔一段时间换一套衣服」，但实际上几乎看不到换装。

两个原因叠加：

1. **当时** `outfitForTime` 的散列键是「年+月+日+小时」，**同一小时内恒定**，
   `day` 时段（9:00–18:00，整 9 小时）会一直穿同一套，一天实际只变 2~3 次。
   （这条描述已不成立：散列键现在是「时间片」，片长 `OUTFIT_SLOT_MS = 30 分钟`。）
2. 更根本的：`PetApp` 的 `showingOutfit` 只在 `outfitMode === 'fixed'` 时为真。
   **自动模式下桌宠平时显示的永远是动作立绘**，服饰只是挂机轮换池里的一个随机项。

所以旧模型其实是「按时间定装 + 偶尔随机露个脸」，和「每隔一段时间换一套」是两回事。

**现在的模型**：动作和服饰进的是**同一个池**，到点换一项，换到哪个算哪个 ——
「换个动作」和「换套衣服」在这里没有区别。间隔由 `settings.petRotateMin` 定
（默认 10 分钟，上限 180），实际等待叠 ±25% 抖动（`rotateDelayMs`），
免得看着像定时机器人。

> **历史注**：这次改的是**桌面轮换**。当时没有动 `outfitForTime` —— 它那时
> 仍按 `OUTFIT_DAY_PARTS` 的时段适配表工作，服务于对话窗旁那个独立立绘小窗
> （`ChatPetApp`）和手机端。
>
> 后来两条路径**已统一为同一套时间片哈希**：都从「已解锁服饰池」里挑、
> 都不看时段，只差片长与池子（`OUTFIT_SLOT_MS = 30 分钟`）；
> `OUTFIT_DAY_PARTS` 已删除。当年记下的取舍（桌宠要「多换几套看看」、
> 小立绘要「此刻她该穿什么」）现在只解释**为什么桌面轮换用纯随机**
> （`pickRotation` 每 `petRotateMin` 抽一次），而不是两条不同的实现。

三个必须记下来的坑：

**① 轮换链会死。** 旧代码在「有台词/表情」时直接 `return` 且**不重排定时器**。
当时间隔只有 1 分钟，撞上的概率低到可以忽略，撞了就当这轮跳过；
改成 10 分钟后，「撞上一次就再也不换」几乎必然发生 —— 而症状是
「轮换彻底不动了」，极难联想到是这个原因。现在改成 20 秒后重试。

同理，onMounted 的首次触发也改走 `scheduleRotation`（原来是裸 `setTimeout`），
纳管进 `idlePoseTimer`，否则窗口销毁后仍会触发一次。

**② 避让不能把池子清空。** `pickRotation` 避开最近三项以免出现 ABAB 卡带感，
但池子本身可能比「最近」还小（最低档只有 4 项）。避让过头会让
`pickLine([])` 返回空串，而空串经 `poseImageFile` 回落到站姿 ——
症状是「立绘突然变回站着」，比重复一次糟得多。所以清空时从原池抽。

**③ 空串会被当成 0。** 设置页是 `v-model.number` 的 number 输入框，
用户清空时给的是 `''`，而 `Number('') === 0` —— 不特判就会被钳到下限 1 分钟，
也就是「一秒钟换一套」。所以 `clampRotateMin` 显式把 `''` / `null` / `undefined`
判为回落默认，钳制也放在**读取侧**（`rotateDelayMs` 里再钳一次），
不指望 input 的 `min`/`max` 能挡住。

#### 「每个都会轮换用到」——深夜不能用硬过滤
深夜/早八（23:00–09:00）原本**排除**非困倦动作，只留 `TIRED_POSES`。
这在「让每张图都用上」的目标下是错的：那个时段占一天近 10 小时，
被排除的 7 项（snack / music / coffee / shrug / heart / surprise / shy）
等于半天都看不到 —— 满级池从 19 项掉到 12 项，最低档更是只剩 2 项。

现在改成**加权**（`weightedPool`，困倦项 ×4），仍然偶尔出现其他动作：

```
满级池 19 项 → 深夜仍是 19 项，只是 yawn/sleep/think 更频繁
```

`weightedPool` 用重复填充实现，而不是给 `pickLine` 加权参数 ——
后者会污染所有调用方，而这个需求只有轮换场景有。

单测里跑了「白天 2000 次 + 深夜 2000 次」的模拟，断言**每个不同项都被抽到过**
（`白天轮换覆盖全部项` / `深夜轮换也覆盖全部项`）。

#### 轮换池可自选，但必须夹在已解锁范围内

用户能在设置页勾选参与轮换的动作与服饰（`petRotatePool`）。规则只有三条，
但每条都有它非这样不可的理由（`resolveRotationPool`）：

| 输入 | 结果 | 为什么 |
|---|---|---|
| 空数组 | **全部已解锁** | 空选若解释成「什么都不换」，`pickRotation` 无候选 → 立绘回落站姿，看着像 bug。真正的「不轮换」由 `outfitMode='fixed'` 表达 |
| 勾了部分 | 交集 | 自选是**收窄**，不是**放宽** |
| 勾的全是未解锁项 | 回落全池 | 老库里可能存着「亲密度被重置前」选的项；此时行为应等于「没自选过」，而不是变哑巴 |

**为什么还要按已解锁二次过滤**：`petRotatePool` 是持久化设置，而解锁状态会变
（清空数据、上帝模式关掉、换会话）。设置页只让勾已解锁的，但那挡不住
直接改数据库或换档位 —— 过滤必须落在**读的那一侧**。
这与 `currentOutfitSlug` 里「未解锁回落默认」是同一条纪律的不同形态。

选择器只列已解锁的项，连灰显的都不列：用户能勾的都必须是真会轮到的。

#### 上帝模式：读时覆盖，不写库

`godMode` 一个开关同时打开三件事：图鉴全解锁、亲密度满档、轮换池给到满级。
它们看起来是三份数据，实际都走同一个门控 —— `affinityView().voice`。

**必须是读时覆盖**。若把亲和度或解锁列表真的写进数据库，就再也分不清
「这一档是我处出来的」还是「模式给的」，而且想恢复真实进度只能清空全部数据。
覆盖只影响读：`affinityView` 在 `godMode` 为真时把 voice 顶到最高档（`soulmate`），
service 的 `gallerySnapshot` 把 `unlocked` 换成全表。两个函数都在读路径上，
关掉开关立刻回到真实状态，数据库一个字节没动。

图鉴只覆盖 `unlocked` / `got`，**不动 `mem`**：记忆是「解锁时她说过的话」，
凭空造出来会污染图鉴文案，也会让解锁剧情提示词拿到假的当前穿着。

#### 清空全部数据：DELETE 而非删库文件

`wipeAll` 清空 8 张表但**保留库文件与表结构**，三个原因：

- 删文件要求无连接持有，Windows 上文件锁很容易 EPERM；
- 重建连接要动 service/index.js 的实例生命周期，而 service 是模块级单例；
- 保留后 `getSettings()` 自然回落 `DEFAULT_SETTINGS`（它本来就是
  `{...DEFAULT_SETTINGS}` 合并存下来的行），效果与「刚装好」一致。

表清单 `WIPE_TABLES` 与 `SCHEMA` 放在同一个文件，且**子表在前**
（`chat_messages` → `chat_sessions`）。虽然写了 `ON DELETE CASCADE`，
但那只覆盖**声明了级联**的那一条；顺序颠倒会在将来新增外键时直接抛约束错误。
smoke 里有两条守卫从 `SCHEMA` 正则抽表名对账，防止「加了表忘了登记」——
那种漏登记的表现是「清空跑成功了但新表还在」，比报错隐蔽得多。

清完必须**重建会话**：全空时 `currentSessionId()` 拿不到会话，
所有读路径返回 `undefined`，界面静默空白（不报错，最难查）。

**关机自启不在清理范围内**：那是 Windows 启动项，不属于「本地数据」。
设置回落默认后 `autoStart` 变 false，下次启动的对账逻辑会把它摘掉。

#### 「用了没导入」——自由变量在 ESM 里不报错

`PetApp.vue` 用了 `weightedPool` 却没 import，而它**只在深夜分支里被调用**
（`isTiredHour()` 为真）。后果：

- Vite 打包不报（自由变量在 ESM 里只在**执行到**那一行才抛 ReferenceError）；
- 单测不报（不渲染 .vue）；
- 每天 23:00–09:00 抛一次，且异常发生在 `scheduleRotation` **之前** ——
  一次就再也接不上，必须重启进程。症状是「深夜桌宠不动了」。

smoke 原来有一条「跨模块函数都已导入」的守卫，但只硬编码了 6 个 store 函数，
恰好漏掉 `@shared/interactions.js`。现在改成**从模块导出自动推导**，
扫全部 `.vue`（`interactions 导出用而未导入（防 ReferenceError）`）。
这条守卫能抓住原 bug 已验证：临时删掉 `weightedPool` 的 import，它立刻报
`src/renderer/src/pet/PetApp.vue: weightedPool`。

> 写这类守卫时注意：要先剥注释和字符串字面量，否则注释里提到的函数名
> 会被当成调用，产生一堆假阳性。

#### 对话窗立绘必须放在窗外

对话框宽只有 420px，立绘浮在消息流右侧**必然压到文字**。
所以立绘是个**独立的无边框窗口**（`ChatPetApp` + `chatpet` 路由），
贴在对话框左侧；左边放不下会自动翻到右侧。

配套细节：

- 对话框 `move` / `resize` 时立绘窗跟着走，`closed` 时一并销毁（不留孤儿窗）
- `setFocusable(false)` —— 它只是装饰，抢焦点会打断打字
- 对话框内保留「👗 当前穿着」换装入口，显隐另给一个「🪟」按钮

## 手机端立绘：服饰与动作交替

19 张立绘分两个**正交维度**：

| 维度 | 数量 | 内容 |
|---|---|---|
| 服饰（`outfits/`） | 17 | 穿什么 |
| 动作（`poses/`） | 18 | 在干什么 |

桌面端一直两个都用了（动作早期按亲密度分档，后来改成初始全给），但手机端早期只上服饰 ——
18 个动作立绘全部闲置，她永远一个姿势，像张静态贴图。

现在顶部立绘在两者间**交替**（一张图没法同时表达两件事）：

- 相位按**分钟**翻转，配 30 秒定时器，保证到点就能看到变化
- 动作按 5 分钟一档轮换，避免每分钟跳一次太躁
- 只在页面可见时刷新（后台跑定时器是白耗电，回来时姿势突变也像 bug）
- 动作池按时间段选：深夜只有「打瞌睡/打哈欠」，
  不然会出现「穿着睡衣却在蹦跳」这种违和组合

## 图鉴系统（装扮 24 套 + 生活照 23 组）

聊天中自然解锁：聊到相关话题，她会主动发照片给你。

### 触发刻意分三层，为省 token

```
① 条件解锁    亲密度 / 时段等硬条件   → 零成本，直接给
② 关键词预筛  本地字符串匹配          → 零成本，不命中就结束
③ 模型判断    只为「候选」调一次 API  → 唯一花钱的一步
```

三个省钱点：

- **已解锁的永不参与判断** —— 候选集合随进度变小，越用越省
- **关键词不命中就不调模型** —— 绝大多数轮次在 ② 就结束了
- **一次请求判断全部候选** —— 不是每个候选调一次

装扮与生活照**共用同一份管线**（`shared/gallery.js` 的 `createGalleryRunner`，
按 `kind` 参数化；类目表 `GALLERY_KEYS` 也在 shared）。
复制两套的话，改一处忘一处，就会出现「装扮省了 token 但生活照忘了省」。

**关键词预筛那一步必须把亲密度传进去**（`keywordCandidates(text, unlocked, points)`）。
预筛里就带着门槛判定，漏传时 `points` 默认 0，于是**门槛大于 0 的装扮/照片
永远进不了候选** —— 表现是「聊到了关键词也永远不解锁」，而且毫无报错、
不花 token、日志里什么都看不到。条件解锁那一步一直是传的，预筛这步漏过。

**解锁会给一笔亲密度奖励**（`AFFINITY_GAIN.photoUnlock = 8`，来源 `unlock`）：
不占聊天额度也不占桌宠额度，且不封顶（解锁是低频事件，不需要防刷）。
奖励失败不影响「已经解锁」这个事实，所以单独 try。

### 「查看大图」必须两端都是全屏

移动端一直是**全屏**查看器（`mobile/style.css` 的 `.viewer`：`position: fixed; inset: 0`，
图 `max-height: 100%`，配标题/翻页/工具条）。
桌面端却是一张 **380px 窄卡片、图最高 300px** —— 立绘和照片在这个尺寸下都看不清，
「查看大图」名不副实。同一个功能两端观感差一大截，用户自然会问「为什么这边看不清」。

现在桌面端也改成**点整格直接进全屏**（跳过中间那层窄卡片），
文字与触发规则挪到全屏层底部：

```
.viewer       position: fixed; inset: 0   ← 全屏遮罩
.viewer-stage flex: 1; min-height: 0      ← 吃掉剩余高度
.viewer-img   max-width/height: 100%      ← 不写死 px（写死就是「小图」的根因）
.viewer-foot  max-height: 38vh; overflow-y: auto   ← 文字过长不挤图
```

用 flex 纵向三段（头/图/尾）而不是绝对定位：图区 `flex:1` 自动吃掉剩余高度，
文字多长都挤不掉图。

**未解锁的项走同一层**（图位换成问号剪影 + 线索）。不拆成两个组件，
是因为「锁着的」和「解锁的」只差一个图位，分两套必然慢慢走偏。

配套细节：

- 桌面是键鼠环境，**Esc 关闭 / ←→ 翻页**必须有（图片放大后去够右上角那个 ✕ 很累）；
  监听挂 `window` 而不是容器 —— 容器没有焦点，`@keydown` 收不到，
  加 `tabindex`+`autofocus` 又会抢焦点。**记得在 unmount 解绑**，否则反复进出会累积监听。
- 卡片右下角给一个 hover 才亮的放大角标（`⤢`）：一直亮会盖住图片内容，
  但完全不给的话没人知道卡片能点。

smoke 里有一条守卫断言**两端 `.viewer` 都是全屏**且图片都不写死高度 ——
只断言这个本质，不管用 flex 还是 grid、有没有工具条（那些各端本就该不同）。
谁把其中一端改回小卡片，那条就会红。

> 图鉴曾有第三个类目「视频」（`videoStories.js`，15 段），已整体移除。
> 它占 16MB 素材、且需要用户在聊天中解锁才有机会看到，
> 性价比不如照片。移除时把这套断言保留并转到了装扮上
> （关键词不得含单字、`condition` 字段必须都实现）——
> 那两类故障与内容形式无关。

## 提示词顺序必须「稳定在前、易变在后」（省 50 倍）

DeepSeek 有**前缀缓存**：命中 $0.003/M，未命中 $0.15/M —— **差 50 倍**。
而前缀缓存是**从头逐字匹配**的，开头一变，后面全部重算。

```
✗ [时间块(300字)][人设(1560字)]
     ↑ 每分钟都在变 → 后面 1560 字人设每轮按全价重算

✓ [人设(1560字)][时间块(300字)]
     ↑ 稳定 → 命中缓存，只有末尾的时间块按全价
```

**实测证据**（同一人设，只改变化位置）：

| 情况 | cached | miss |
|---|---|---|
| 前缀不同 | **0** | 1003 |
| 前缀相同 | **768** | 234 |

所以代码里顺序是 `composeSystemPrompt(persona, clock)` ——
`chat.js` 里有一个专门的 helper 承载这条规则，避免有人散在几处改错。

**换序的代价与补偿**：时间块不再占开头，模型对它注意力略降。
实测出现过「23:40 被读成 11:40」。补偿办法是在时间块里**显式给出两种表述**：

```
现在是 2026 年 9 月 21 日 周一，**23:40（24 小时制）**，也就是深夜11:40。
```

加上时段词（深夜）后复测 5/5 全对。
`smoke.js` 有守卫断言顺序 + 24 小时制消歧，改回旧顺序会立刻失败。

## 她必须「知道自己知道时间」

**症状**：问她「现在几点/周几」，她含糊其辞或答错。

**先排除的假设**：注入路径一直是好的 —— 时间块每轮都注入 system 末尾，
日期/星期/时刻都正确，长对话 30 轮后依然在。
所以问题不在「没给她时间」，而在**提示词没让她意识到自己知道**。

**原提示词的缺陷**：整段「时间感」只写「**不要**说什么」
（不要提早午饭、不要报时…），从没写过「**你确实知道现在几点**」。
再叠加「不要频繁报时」这条，模型很容易把时间块理解成
「约束我行为的背景设定」而不是「一个我可以说出来的事实」。

于是被问时间时，它会绕开或瞎猜。

**修法：把「时间感」从纯禁止改成主动认知**

```
- 系统会在对话开头给你「当前时间」，那是真实的此刻，不是设定、不是示例。
- 你确实知道现在是几点、周几、几号。被问到就直接照实说
  （「现在下午三点多啦」「都周一了」），不要含糊、不要反问、不要说自己不知道。
- ...
- 除了被问到、或话题自然带到，平时不用主动报时 —— 它是给你校准行为用的。
```

注入块同步改了措辞：标题从「必须严格遵守」改成「**这是真实的此刻**」，
并加一句「你确实知道现在的时间。如果有人问你几点、周几、几号，
照上面直接回答，不要含糊或反问」。

**实测（真实 API）**：

| 场景 | 回答 |
|---|---|
| 周一 14:15 问几点 | 「两点十五，下午。你那边刚上完课还是也在摸鱼？」 |
| 周一 14:15 问周几 | 「周一呀，下午两点多，正上课呢😩」 |
| 周一 07:30 | 「现在早上七点半啦，周一。这个点你怎么醒的，赶早八吗？」 |
| 周一 23:40 | 「周一，都快十二点了，23:40 啦。你还没睡？我是在赶明天要交的作业……」 |
| 周六 15:00 | 「下午三点啦，今天周六～」 |

**通用教训**：只写禁止项，模型会「回避」而不「掌握」。
涉及「她应该知道某个事实」时，必须正面声明她知道，
否则禁止项会被误读成「这个话题不能碰」。

## 多模态：让她看图

后端支持图片输入（`deepseek-flash` 原生多模态）。图片可以**选文件 / Ctrl+V 粘贴截图 / 拖拽**进来，
发送前用 canvas 压到长边 1280 再转 data URL。

### 三个必须遵守的服务端约束

来自 DeepSeek 官方 vision 文档，任何一条搞错都会 400 或产生隐性浪费：

1. **图片只能出现在 user 消息里**。放 system / assistant 直接 400。
   所以 `normalizeForRequest` 会把非 user 消息里的图剥掉。
2. **只有最后一条 user 消息保留图片**，历史图降级成 `[图片×1]` 文字占位。
   不这么做的话，每轮都重发所有历史图片（每张最多 1024 token），
   聊几轮就把上下文预算吃光，费用也跟着涨。
3. **格式按文件内容判定，不看扩展名**。所以校验只认 data URL 里的 MIME，
   不去猜文件名。

### 内容块形态

`content` 有两种合法形态，按有无图片自动选择：

```js
'你好'                                        // 纯文本：保持字符串
[{type:'text',text:'看图'},                   // 有图：块数组
 {type:'image_url',image_url:{url:'data:...'}}]
```

没图时**返回字符串而不是单元素数组**是刻意的：让绝大多数请求保持原样，
不给所有调用方（含第三方兼容接口）引入新格式。

落库时序列化成 `{"blocks":[...]}`，纯文本原样存字符串 ——
老数据零迁移，也不需要给表加列。读回时靠 `{"blocks"` 前缀快速判断，
避免每条消息都 `JSON.parse`。

### 字符预算要特殊处理

图片是几百 KB 的 base64，按真实长度算会**瞬间吃满预算**；
但它的 token 成本实打实存在（每张最多 1024）。
所以 `contentCost` 给每张图记一个固定的 2000 字符占位 ——
既不能按原始长度算，也不能当零成本。

### 模型必须支持视觉

`deepseek-chat` 是纯文本模型，发图会 400。与其让用户对着含义模糊的上游报错发懵，
不如发送前拦住并说清怎么改：

```
deepseek-chat 不支持图片，请在「设置 → AI 对话」把模型换成 deepseek-flash
```

判断用**黑名单**（`NON_VISION_MODELS`）而不是白名单：
自定义服务商很可能提供视觉模型（如 `qwen2.5-vl`），白名单会误伤。

这个检查在渲染层也做一次（`onSend` 里），**在清空输入框之前** ——
否则用户打的字和图都丢了，还得重新弄一遍。

## 让她认识自己

**症状**：把她的立绘发给她，她说「这是一位棕发少女」——把自己当陌生人。

**原因**：她从来没见过自己。人设里只写了她是「女大学生」，
没有任何外形信息；而且即使写了文字，模型对自己长相的理解仍然很飘。

**修法：两条路一起走**，缺一条效果都不够稳。

### 1. 人设里的 `【你的样子】`

```
- 棕色长卷发，齐刘海，发量偏多，发尾微卷
- 红棕色的眼睛，皮肤白
- 常穿：白色针织连衣裙、白上衣配黑短裙、红色外套…
```

纯文字，零 token 成本（就几十字）。

**必须同时写「不像就不是我」的否认规则**：只教她认自己，
模型容易变成硬认 —— 别人发张网图也说「这是我」。

### 2. 参考图注入（`withSelfPortrait`）

给一张真实立绘，让她用视觉能力**亲眼看过自己一次**。请求长这样：

```
[system]    人设（含【你的样子】文字描述）
[user]      [自己的立绘] + 「上面画的**就是你**，记住自己的样子」
[assistant] 嗯，记住了，这是我。
[user]      用户的图片 ← 现在她能认出这是自己
```

三个关键设计：

1. **图片只能放 user 消息**（官方 vision 硬约束），所以套成 user/assistant 一对。
2. **配一句 assistant 回执**。只放一条孤立的 user 图 + 说明，容易被模型
   当成「待处理任务」；有来有回才像自然的对话历史。
3. **注入在 `trimByChars` 之后**。反了的话参考图会被当成最早的历史裁掉 ——
   白花 token 还没效果。

**成本**：每轮约 +1024 token（图片上限）。可接受，但也因此只在
模型支持视觉时注入 —— 纯文本模型收到图会直接 400，
所以 `deepseek-chat` 下自动跳过（那时退化成人设里的文字描述）。

参考图用哪张由 `SELF_PORTRAIT_SLUG` 决定（默认 `pose4` 正面站姿最清晰），
文件从 `dist/yuki-<slug>.png` 读，缓存一次后复用。

**路径解析放在主进程**（`loadSelfPortrait` 注入给 service）：
资源路径依赖打包方式（开发时在 `src/renderer/public`，打包后复制到 `dist/` 进 asar），
而 service 刻意不感知这些。读不到就返回空串 —— 没有参考图也能正常聊。

## 主动说话（气泡）的来源：两种内容混着说

> 这一节只讲**主动说话**（`generateChatterLine`，桌宠气泡里那句、不入库）。
> 另一条路径「主动找话题」`generateTopicLine` 直接走模型，**不**从台词库挑，
> 分工见「主动说话不入库、主动找话题才入库」。

自动说话有**两个来源**，按 6:4 随机选用，而不是「模型优先、失败才用台词库」：

| 来源 | 内容 | 权重 |
|---|---|---|
| `history` | 结合**最近两天**的聊天现编一句 | 0.6 |
| `pool` | `linesFor('idle', voice)` 台词库 | 0.4 |

只用一个都不行：全用模型会飘（而且没配 Key 时完全没话说），
全用台词库又和你们的实际聊天脱节。

**连续两次同源会被错开**：连着追问聊天内容有压力，连着说通用台词像复读机。
用 `lastChatterKind` 记住上一次的来源，命名上刻意区分于「生成失败回落」。

### 为什么限定「最近两天」

原先只按**条数**取（24 条），聊得少时会把几周前的内容捞出来，
她照着老话题搭话很出戏。现在是**时间下界 + 条数上限**叠加：

```js
const since = Date.now() - CHATTER_WINDOW_MS   // 2 天
const history = store.messagesSince(latest.id, since, 200)
```

两个都不能省：时间界定「多久之前算旧事」，条数防止两天内聊了几百条撑爆上下文。
两天也是刻意选的——够覆盖「昨天聊到一半的话题」，又不会拉回一周前。

两天内没聊过时**不再直接放弃**。原先这里 `return { ok: false, reason: '最近两天没有聊天内容' }`，
由调用方回落到台词库；后果是隔两天不聊，主动找话题永远走不到模型那一步，
而台词库那句**不入库** —— 用户看到的是「她不主动发消息、也没有未读红点」。

现在两个函数都换成「没有上下文」时的提示词：

- **主动找话题**让她**开个话头**，并**照常落库**（同一条入库路径，有未读、进消息列表）
- **主动说话**退回「自言自语」模式（`fromHistory: false`），仍然不入库

「让她对着一周前的旧事搭话，比说一句通用台词更奇怪」这个判断没变，
但解法从「回落到通用台词」改成了「开新话头」—— 后者才是真人会做的。

## 自定义人设

内置人设写死在 `CHAT_PERSONAS`，用户自建的存 `personas` 表。

- 「复制」会连提示词一起复制成可编辑副本，并自动切过去
- 删除正在使用的人设会回落到默认，不会让人设变成空白
- `resolveChatConfig(settings, customPersonas)` **必须带上自定义列表**，
  否则自定义人设会被静默忽略、回落成 Yuki

## 桌宠窗口尺寸约束（内容驱动贴合）

右键菜单已迁**独立小窗**（petmenu，常驻隐藏、右键时定位到光标并按工作区钳制，
失焦/Esc 收起），不再和桌宠挤同一个窗口——旧方案里「菜单+气泡+桌宠同窗、
窗口尺寸要同时容纳三者」的约束随之作废（那段历史留痕：220×260 时代菜单只能
看见下半截，后来 340×700 给菜单预留了整段高度，都是同一问题的迭代）。

现在桌宠窗 = **内容包围盒**：渲染层 ResizeObserver 量 `.stage`（气泡+把手+立绘）
的实际尺寸，报给壳层按右下角锚定重设窗口（`pet:refit`）。壳层不维护尺寸公式，
`petScale` 只影响渲染层的 CSS 缩放，窗口由内容自然撑开。

菜单窗自己的高度也用同一套机制（`menu:resize`，渲染层量面板高度报给壳层，
顶边不动），菜单内超长内容 `overflow-y: auto` 兜底。

**第三个窗是对话窗旁的立绘小窗**：`chatpet:resize`（渲染层量 `.cp-root` 的高度
报给壳层）。它和上面两个的锚定方向**不同 —— 是底边锚定**：立绘站在窗口底部，
换装面板在立绘上方展开，所以内容变高时窗口**向上长**、底边不动
（改顶边会让她的脚每次开合面板都上下跳）。收起时上报高度 `0` 而不是
`offsetHeight`，理由见 `ChatPetApp.vue` 的注释（`.cp-root` 是 `min-height:100vh`，
直接报量到的高度会让窗口高度单调不减，多出来的透明区还会吞掉点击）。

> **已知缺口（待办）**：这条规则目前是 **Electron-only**。
> `src/renderer/src/lib/desk-shim.js` 只登记了 `refitPet` / `resizePetMenu`，
> **没有 `resizeChatPet`**；`src-tauri/src/windows.rs` 也只有 `pet_refit` /
> `pet_menu_resize`，没有对应的 `chatpet_resize` 命令。
> 于是 `ChatPetApp.vue` 里的 `window.desk?.resizeChatPet?.()` 在 **Tauri 下是
> 静默 no-op**，换装面板仍会被窗口边界裁掉（症状就是「只看到一道阴影」）。
> 补齐要同时加 Rust command 并注册进 `generate_handler!` —— 属已知待办，
> 别以为 Tauri 侧也有了。

## 摸鱼收入算法

```
日薪      = 月薪 / 本月工作日数
计薪时长  = (下班 - 上班) - 每日休息时长
已计薪    = clamp(现在 - 上班, 0, 在岗时长) × 计薪时长 / 在岗时长
今日收入  = 日薪 × 已计薪 / 计薪时长
```

- **本月工作日数按真实日历数**，不用固定的「双休 8 天」这类套餐值——2025-06 双休实际是 21 个工作日，套餐值会算成 22，日薪整体偏低约 5%。
- 休息日（双休/单休/大小周/不定休）当天收入恒为 0。
- 状态机：`尚未开工` → `摸鱼进行中` → `今日已赚满`，休息日走 `今日休息`。

## 偷偷摸摸模式（学习化伪装）

设置开关 `studyDisguise`（设置页「偷偷摸摸模式」）。**语义（方案 A，已拍板）**：
开启后任何界面都不出现真实金额——伪装是给「路过者扫屏幕」用的，不是给自己
换算便利；要看钱就关开关。

**架构：伪装在数据出口统一生效，组件禁止就地三元判断。** 单一出口是
`src/shared/disguise.js`（词汇表 `SURFACE_TEXT`/`surfaceText` + 换算
`formatStudyProgress`），`service.getState` 组装 `todayEarnedText` /
`dailySalaryText` / `salaryText` 时按开关转换。这样气泡、Sidebar、HomeView、
托盘（两壳）全部自动覆盖——历史上「标题换皮、金额裸奔」的 6 处穿帮，就是
组件各自三元判断漏掉的。

- 换算规则：`已背 N 词 = round(今日已赚 ÷ 日薪 × 1000)`，一天从 0 走到
  1000 词，与进度条天然对齐；日薪非正时保守封顶防除零。
- 「摸鱼」字样集中在词汇表映射（摸鱼→学习、已赚→已背/目标、等级名
  `studyLevelName` 按词替换、HomeView 语录换学习风文案）。
- **新增可见文案先在词汇表登记**，组件按 key 取，禁止新写
  `studyDisguise ? A : B`；smoke 锁「伪装词汇表与 state 三字段不得含
  摸鱼/已赚/¥」，改漏了 CI 直接红。
- 语义边界（有意保留）：设置页/研究院计算器/打卡记录是**操作面**，用户
  主动打开并输入，保留真实值；托盘 tooltip 与进程名的「摸鱼桌宠」属系统
  身份，无法伪装也不在此范围。
- 气泡状态行是**纯状态**（「摸鱼进行中」），不复述金额——金额只在
  bubble-amount 出现一次，状态行带金额是首版信息设计遗留的冗余。
- 台词（台词库「再摸要收费了哦」类、LLM 现编）暂不在伪装内：涉及「提示词
  稳定在前」约束，二期随对话提示词单独做。

  （store.js / store-bridge.js）同式推进 `PRAGMA user_version`，结构性变更
  走迁移段（幂等、显式事务）；**禁止只改 SCHEMA 不加迁移**——
  `CREATE TABLE IF NOT EXISTS` 对存量库零作用。
- `checkins.dateKey` 是 partial unique index（`WHERE deletedAt IS NULL`），
  不是列级 UNIQUE——列级约束不排软删行，删过的日期会被死行永久锁死。
- `pendingChanges()` 与 `markSynced()` 的表清单（含 personas）在两后端各
  一份，新增业务表必须四处同步；`markSynced` 表名走白名单（该通道对渲染层
  开放，键名直拼 SQL）且不改写 `updatedAt`（增量推拉按它判新旧）。

补卡写入的 `checkins.note` 为「补卡」，和现场打卡区分开。

`meta` 里存了几个跨表状态：`affinity:<sessionId>`（亲密度，按会话隔离；旧全局
`affinity` 键首次读取时迁移清除）、`activeSessionId`（当前活跃会话）、
`set:<key>:<sessionId>`（逐会话设置：人设/穿着/图鉴开关）、
`holiday-<year>`（按年缓存的节假日表）、`petPosition`（桌宠位置，
`{x, y, w, h, v:4}`——右下角锚点语义，见「桌宠窗口尺寸约束」一节）。

云端接入时只需：`pendingChanges()` 取增量 → 推送 → `markSynced(ids)`。
不需要改表结构，也不影响离线使用。

数据库落在 `%APPDATA%\desk-pet\desk-pet.db`（两壳共用同一份）。

## 安全边界

**Electron 壳**：

- `contextIsolation: true`、`nodeIntegration: false`、五窗全部 `sandbox: true`（preload 只用 contextBridge + ipcRenderer，开 sandbox 零成本），渲染进程只能用 preload 白名单暴露的 `window.desk`。
- 主进程 IPC 全部走 `ipcMain.handle`，按 channel 白名单注册，无动态转发。
- **导航防护**：`web-contents-created` 统一挂 `setWindowOpenHandler` deny + `will-navigate` 白名单（file:// 与 dev origin）——渲染层一旦被注入，远端页面不能带着 preload 拿到 `window.desk` 全部通道。
- **API Key 脱敏口径**：`chatApiKey` 原文只在两处可达——settings 表（本机）与 `settings:getFull` 通道（设置页按需拉取）；state 快照、`session:settings` 及一切广播均剥掉 Key。新增返回设置的通道必须保持该口径。
- 打包即 fuse 加固（RunAsNode / NodeCliInspect / NodeOptions 全关，build.js 内翻转、失败即终止）：`DESK_DEBUG_PORT` 门控只管应用自开的调试口，挡不住外部 `ELECTRON_RUN_AS_NODE=1` 直启。

**Tauri 壳**：业务层跑在 pet 窗 webview 里（`service-host` 直建 service），
其他窗经 `service-bus`（`bus:req`/`bus:res` 事件对，就绪 ping 门控）转发到 pet 窗；
系统能力走显式注册的 Rust command（窗口/托盘/rusqlite 桥/HTTP 代理），
contextIsolation 同样开启、无 Node 注入。

- **app 自定义命令不经 ACL**：Tauri 2 的 capabilities 只管 plugin 命令，
  `db_exec/db_select/db_batch/http_*/tray_update_snapshot/photo_list` 的
  「仅 pet 窗」靠命令入口 `ensure_pet_window` 按调用窗 label 校验实现。
  **新增敏感命令必须同样收权**——不收权等于对全部 webview 开放。
- CSP 已配置（default-src 'self' 等，img/media 放行 asset 协议）；新增
  远程资源类型时先过安全审查再动 CSP。

两壳共同点：不联网、不上传，全部本地读写（节假日表与 AI 对话按用户配置出网）。

**版本号四处一处不少**：package.json / src-tauri/tauri.conf.json /
src-tauri/Cargo.toml / scripts/installer.nsi，由 `scripts/check-version.js`
（挂 `npm test`）锁一致——历史上手改漏过 Cargo.toml，发版 tag 只读
package.json，错版产物会照常上 Release。

## 设置保存必须脱 Vue 响应式代理

**症状**：设置页点「保存」必失败，报 `An object could not be cloned.`。
迷惑之处在于**改哪个字段都一样失败**，看起来像「保存按钮坏了」。

**根因**：Vue 的 `reactive` 是**深**的。设置页的 `form` 是
`reactive({ ...DEFAULT_SETTINGS })`，而 `DEFAULT_SETTINGS` 里有 `chatBgPool: []`，
所以 `form.chatBgPool` 是**数组 Proxy**。`{...form}` 只是**浅**展开 ——
顶层成了普通对象，嵌套值仍是 Proxy。Electron 的 `ipcRenderer.invoke`
走 structured clone，遇到 Proxy 直接抛 `DataCloneError`。

**为什么一直没被发现**：

| 调用方 | 传入内容 | 结果 |
|---|---|---|
| 设置页 `save()` | `{...form}`，含 `chatBgPool` 数组 | ✗ 必炸 |
| 对话窗 / 右键菜单换装 | `{ outfitMode: 'auto' }`，全原始值 | ✓ 正常 |

也就是说**决定成败的不是「刚改了哪个设置」，而是「传的值里有没有对象/数组」**。
所以症状看起来像「只有设置页坏了」，实际是两个调用方传的东西不同。

**修法**：`saveSettings` 里统一过一道 `plainForIpc`（JSON 往返），
而不是在各个调用点各自处理 —— 漏斗只有一处，Proxy 进不来。

两条纪律：

- **不要用 `toRaw`**：它只脱最外层，嵌套 Proxy 原样留着，治不了本。
- **归一化放在漏斗**，不要散在各调用点：设置页就有 3 处 `saveSettings({...form})`，
  漏一处就只在那一种场景复现。

JSON 往返是安全的：设置本来就是逐项 `JSON.stringify` 存进 SQLite 的
（`store.saveSettings`），往返与落库表示完全一致。

> Tauri 壳不受影响 —— 它不走 structured clone。改这块时别以为「两边都会炸」，
> 也别因为「Tauri 没事」就在 Electron 上漏掉。
